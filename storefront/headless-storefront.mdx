A headless storefront is a site you build and host yourself that sells through Fluid. Fluid stays the source of truth for products, content, carts, checkout, and rep attribution. Your app decides how the store looks and where it runs.

Fluid publishes a starter you can copy: [Fluid-WeCommerce/headless-wecommerce](https://github.com/Fluid-WeCommerce/headless-wecommerce), a Next.js app under the MIT license. Set one environment variable to your company's Fluid subdomain and it renders the whole storefront: home, shop, products, enrollment packs, media, libraries, categories, collections, blog, pages, cart, and search.

<Info>
  This guide covers a storefront that uses Fluid's hosted checkout. To build
  the checkout yourself as well, see [Build a headless
  checkout](/api/guides/headless-commerce).
</Info>

## How it fits together

The starter splits the work between your server, the browser, and Fluid:

| Part | Runs on | What it does |
| --- | --- | --- |
| Your Next.js app | Your server | Reads products and content from the public storefront API, renders every page, and caches the responses. |
| FairShare SDK | The shopper's browser | Records page views, attributes visits to reps, and keeps the cart. See [FairShare SDK and the storefront](/storefront/fairshare-sdk). |
| Fluid checkout | Fluid | Takes payment and places the order. The SDK hands the cart over with the shopper's session, so checkout works from any domain. |

The app reads only the public storefront endpoints, which need no token. See [Public and company endpoints](/storefront/public-and-company-endpoints).

## Run it locally

You need Node.js 20.9 or later, pnpm, and your company's Fluid subdomain: `acme` if your store is at `acme.fluid.app`.

<Steps>
  <Step title="Copy the starter">
    ```bash
    git clone https://github.com/Fluid-WeCommerce/headless-wecommerce.git my-storefront
    cd my-storefront
    pnpm install
    ```
  </Step>
  <Step title="Point it at your company">
    Copy the example settings and set `FLUID_SHOP` to your subdomain.

    ```bash
    cp .env.example .env.local
    ```

    ```bash .env.local
    FLUID_SHOP=acme
    ```
  </Step>
  <Step title="Start the dev server">
    ```bash
    pnpm dev
    ```

    Open `http://127.0.0.1:3000`. You see your store's products, content, languages, countries, and brand colors.
  </Step>
</Steps>

<Warning>
  Test checkout at `http://127.0.0.1:3000`, not `http://localhost:3000`. On a
  hostname that contains `localhost`, the SDK sends checkout to a local Fluid
  checkout server instead of Fluid's hosted checkout. Deployed sites aren't
  affected.
</Warning>

## Deploy it

The starter is a standard Next.js app, so it runs anywhere Next.js does.

- **Vercel.** Use the **Deploy** button in the repository's README, or import the repository, and set `FLUID_SHOP`. Add your domain under the project's domains. Canonical URLs and the sitemap follow the production domain.
- **Any Node.js host.** Run `pnpm build`, then `pnpm start`. Set `NEXT_PUBLIC_SITE_URL` to the storefront's public URL so canonical URLs and the sitemap use it.

### Settings

Only `FLUID_SHOP` is required. `.env.example` lists every setting.

| Variable | What it does |
| --- | --- |
| `FLUID_SHOP` | Your company's Fluid subdomain. |
| `NEXT_PUBLIC_SITE_URL` | The storefront's public URL. Detected automatically on Vercel. |
| `FLUID_COMPANY_PRIVATE_TOKEN` | Optional. A company token that lets the header and footer use your Fluid website navigation menus. Keep it on the server: never prefix it with `NEXT_PUBLIC_`. |
| `FLUID_REVALIDATE_SECONDS` | How long to cache Fluid data. Defaults to 300 seconds. |
| `REVALIDATE_SECRET` | The secret for the on-demand cache refresh. See [Keep pages fresh](#keep-pages-fresh). |

## URLs and rep credit

Pages use the same URLs as a Fluid-hosted storefront, so existing links, shares, and QR codes keep working. Every page sits behind the credit segment: a rep's username, such as `/jordan-lee/products/beet-blend`, or `home` when no rep is named, such as `/home/products/beet-blend`.

Links keep the shopper's credit. A shopper who arrives on `/jordan-lee/shop` stays on `/jordan-lee/...` as they browse, and the SDK attributes the visit to that rep. Canonical URLs and the sitemap use `/home/...`. See [Storefront URLs and the credit path](/storefront/fairshare-sdk#storefront-urls-and-the-credit-path).

## Build your own templates

The starter has a folder under `src/templates` for each Fluid template type, such as `product`, `enrollment_pack`, `medium`, `library`, `collection`, `category`, `post`, and `page`, plus the page types such as `home_page`, `shop_page`, and `cart_page`. Each folder has a `default.tsx` and an `index.ts` that registers its templates.

A record picks its template by its slug:

1. If the folder's `index.ts` registers a template under the record's slug, that template renders.
2. Otherwise, `default` renders.

```ts src/templates/product/index.ts
export default defineTemplates<"product">({
  default: ProductDefault,         // every other product
  "beet-blend": ProductLanding,    // /home/products/beet-blend
});
```

The template a merchant picks in Fluid Admin isn't used. Your storefront's design lives in your code. If a merchant changes a record's slug, update the key or the record goes back to `default`. See [Slugs and URLs](/storefront/slugs-and-urls).

Templates are built from sections in `src/sections`, which are built from components in `src/components`, the same layering as a Fluid theme.

## Languages and countries

The storefront offers the languages and countries your company has enabled in Fluid, and a picker in the header lets shoppers switch. It chooses a shopper's locale the same way a Fluid-hosted storefront does: the `lang` and `country` query parameters, then the locale cookie, then the browser's language and the shopper's country, then your company's default.

Prices, currencies, and product availability follow the country. Content follows the language. The SDK and checkout read the same cookie, so the cart and checkout stay in the shopper's language and country. See [Translate storefront resources](/storefront/translations) and [Country availability](/storefront/country-availability).

## SEO

Every page gets a title, meta description, canonical URL, Open Graph and Twitter tags, and `hreflang` alternates, from each resource's `seo` settings in Fluid. A resource Fluid marks as not indexable gets a `noindex` tag. Products, posts, and the site carry schema.org structured data, and the app serves `/sitemap.xml` and `robots.txt`. See [SEO for storefront resources](/storefront/seo).

## Cart and checkout

The starter loads the FairShare SDK on every page, the same bundle Fluid-hosted themes use. Shoppers add to the cart with Fluid's cart drawer, and **Checkout** hands the cart to Fluid's hosted checkout. To build your own cart UI, use the React hooks in `src/lib/fairshare/hooks.ts`. See the [FairShare SDK](/sdk/overview) for every cart method.

## Keep pages fresh

The app caches Fluid's responses for `FLUID_REVALIDATE_SECONDS`. To refresh sooner, send a `POST` to `/api/revalidate` on your storefront with an `Authorization: Bearer` header carrying your `REVALIDATE_SECRET`. To refresh whenever something changes in Fluid, point a [webhook](/api/guides/webhooks) at it.

## What the public API doesn't provide

A headless storefront sees only what the public storefront API returns. Plan for these gaps:

- **Page content.** A page returns its title, description, image, and metafields, but not the content built in Fluid's page editor. Build page content in a template. Metafields are a good home for copy merchants should be able to edit. See [Metafields](/storefront/metafields).
- **Redirects.** Redirects set up in Fluid Admin don't apply. Add them to `next.config.ts`.
- **Navigation menus.** Your Fluid website navigation menus need `FLUID_COMPANY_PRIVATE_TOKEN`. Without it, the starter uses the links in `src/config/site.ts`.
- **Tag manager and analytics.** Add your tags to the app's layout yourself.
- **Theme template choice.** The template a merchant assigns in Fluid Admin isn't returned, which is why templates match by slug.
