<Warning>
  Native widgets use your company’s existing member storefront availability and require deployed, synced native Liquid templates. Confirm availability and supported live actions for your company before publishing a page that depends on them.
</Warning>

## Choose the widget source

Native widgets are supplied globally by Fluid and require no Droplet installation.
Droplet widgets come from an installed Droplet; their catalog entries identify that supplier.
Theme sections remain a separate category for theme-authored content.
The enabled builder separates **Native widgets** and **Droplet widgets** in **Widgets**, and provides **Theme sections**, **Native widgets**, and **Droplet widgets** in the add picker.
Droplet embeds retain their enable/disable controls; placeable widgets are added to a page.

## Place and configure a native widget

Choose a compatible member-page template, open **Widgets**, and drag a native widget onto the page, or select it in the add picker and click **Add section**.
Each placement has its own settings, including size, title, destination, link label, image, image description, product ID, and additional JSON configuration.
Not every widget uses every shared setting; configure only fields that apply to its behavior.
The four size values are `small`, `medium`, `large`, and `extra-large`; they are variants of one widget identity.

A native placement uses a stable URI and a matching schema entry:

```liquid
{% section 'fluid://native/widgets/member', id: 'welcome_member' %}

{% schema %}
{
  "sections": {
    "welcome_member": {
      "id": "welcome_member",
      "type": "fluid://native/widgets/member",
      "settings": { "size": "large", "title": "Welcome back" }
    }
  }
}
{% endschema %}
```

Merge the placement into the existing schema; keep the tag ID, schema key, and entry ID aligned.
Use the global native reference rather than copying its implementation into a theme or replacing it with a same-named theme section.

## Automatic catalog updates

In environments with automatic catalog sync enabled, a successful application deployment queues a background sync of the global native Liquid templates and their settings schemas into the catalog database.
The sync accepts only the currently intended template contents from a matching deployed worker, serializes updates, skips unchanged templates, and retries failures.

It updates global templates without overwriting company template copies or existing placement settings.
It does not delete catalog templates simply because their source files disappear.
If a sync needs recovery, an operator can re-enqueue it from the currently intended deployed release.

The global catalog sync stores complete Liquid markup, styles, and settings schemas in the database; it does not enable the member storefront for a company.

## Liquid rendering and preview

Native sections render their HTML and CSS on the server from the synced Liquid templates, using each placement's settings.
The native section applies the theme's colors, fonts, spacing, and card shape; place the existing section to reuse that styling.
Builder previews render fictional sample data without reading private member records or enabling live actions.
Native rendering uses ordinary HTML and CSS; small inline JavaScript handles supported task actions, attributed sharing, copying links, event countdowns, and calendar exports.
Live rendering checks member storefront availability and authenticated member authorization before reading member-scoped data on the server.
Do not place member credentials, access tokens, private records, or fabricated live results in widget settings.

Additional configuration accepts a JSON object; explicit top-level settings take precedence over overlapping fields in that object.
Use ordinary HTTP or HTTPS destinations for links; unsafe navigation protocols are rejected.

## Follow the original design rules

The original widget kit is a design specification with fictional data, not evidence that a live workflow or integration exists. Use its rules as acceptance criteria when extending a native section:

- Use an 8px grid for dimensions, spacing, and line heights. Keep content aligned to the leading edge and inside the theme inset.
- Across all four variants of one widget, use at most two font families, three text sizes, and three font weights. The original type scale is font size/line height in pixels: 12/16, 14/16, 20/24, 28/32, 40/40, and 64/64.
- Take colors and heading/body fonts from theme tokens. The original design contract specifies a widget radius from 0–40px in 8px steps, falling back to the theme card radius; inset is 16, 24, or 32px, falling back to theme card padding. Its concentric nested radius is `min(outer radius, max(outer radius − inset, 8px))`. These are design requirements to verify, not a claim that every deployed theme enforces them.
- Preserve the four cell footprints: Small 1×1, Medium 2×1, Large 2×2, and Extra large 4×2. The reference uses 176px cells with 16px gaps; these are reference dimensions, not a fixed width for every device.
- Adapt content to the available width and height without clipping or crossing the inset. Follow each widget’s Adapt notes; dropping secondary rows is preferable to hiding the primary action or value.
- Use the original focus treatment: a 2px accent ring with a 2px offset. Test keyboard operation, reduced motion, narrow screens, long labels, and light and dark themes.
- Check every size with different theme insets and radii. The original audit uses layers for grid, inset and areas, structure/loading, type, and final appearance; a screenshot of one size does not establish compliance.

## Connected behavior and limitations

The native data projections cover 22 catalog keys: `sponsor`, `streak`, `nextstep`, `signals`, `live`, `working`, `funnel`, `team`, `tasks`, `today`, `countdown`, `pass`, `chbest`, `chmix`, `chgoal`, `chsales`, `site`, `pulse`, `refs`, `resume`, `course`, and `courses`.
Other widgets can reuse existing account data or company configuration; this count is not a promise that every catalog workflow has a live source.

Buy it again shows previously purchased items from recent owned orders and links to order history. It does not create a new purchase or check current prices and availability.

Next delivery and Subscriptions show the next billing date, not an arrival estimate. The released behavior links to subscription management. In-card skip and undo are pending release and verification; do not promise them for an existing installation.

Sales charts show attributed daily sales in USD with UTC dates; the month-goal projection uses a linear daily pace and is an estimate.
Those sales charts report unavailable data while their statistics await reconciliation.
The sharing heatmap groups tracked visits into UTC weekdays and four-hour blocks over eight weeks; it does not schedule a share or establish an ideal send time.
Product mix shows units on paid attributed orders over 30 UTC days and does not deduct refunds.

The team sunburst renders a bounded portion of the authorized member genealogy on the server, with expandable details for visible branches.
Task widgets request confirmation before completing or reopening an owned task, show errors when a write fails, and refresh after a successful change.
Task mutations and attributed sharing remain disabled in previews.
Clinical, compensation, carrier ETA, signature, and reward-fulfillment presentations need a corresponding authorized provider or additional capability before they can show live results.
A provider-dependent widget can show an unavailable state even though its preview and all four visual sizes exist.

## Action release status

The per-widget reference below records original design intent. It does not assert that each proposed action, data source, filter, or adaptation is implemented in the deployed widget.
CRM extra-large inline replies, content sharing/copying captions and attributed links, subscription skip/undo, and sharing-heatmap scheduling have follow-up work pending release and verification. Keep publication of those promises coordinated with the corresponding release; use the released navigation or unavailable state until then.
Do not infer that a displayed button completes a booking, payment, purchase, message, prescription log, signature, reward, or compensation workflow. Confirm the authorized source, eligible action, successful result, and error handling independently.

## Give agents accurate build instructions

Start from the native catalog entry and the widget's supported settings; reuse the existing native section instead of creating a Droplet just to make it globally available.
Keep the four size variants within one Liquid section and preserve empty, error, and unavailable states.
Use the design rules and the per-widget Data, Tap, and Adapt reference as a checklist. Distinguish original intent, released support, and pending work in the implementation plan; never turn a design-only action into a fabricated success message.
Use authenticated member-scoped data for live widgets and inert sample data for previews.
Treat a rendered card as a presentation implementation, not proof that the complete workflow is connected.
Clinical results, medication adherence, compensation, carrier arrival estimates, e-signature workflows, and reward fulfillment require their corresponding integrations or product capabilities.
When a source is unavailable, show the unavailable state or a clearly configured reduced scope; never substitute preview numbers for live records.

For a custom integration supplied by a Droplet, follow [Droplet widgets](/themes/member-storefront/droplet-widgets) and [Droplet data](/themes/member-storefront/droplet-data).
For member-page context, read [Member Liquid variables](/themes/member-storefront/member-variables).
