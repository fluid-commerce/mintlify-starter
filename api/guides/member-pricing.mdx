Member pricing lets one product carry several prices. A buyer's member type picks a price type, and the price type picks the price.

This guide explains the model. It doesn't restate request and response schemas; the linked API Reference pages own those. For the storefront side, see [Member pricing in themes](/themes/member-storefront/member-pricing).

## Price types

A price type is a named rank of prices that a company sets for its catalog. The API calls a price type a pricing tier, and its identifier field is `pricing_tier_id`.

Every company has three system price types:

| Price type | `tier_level` |
| --- | --- |
| Retail | 0 |
| Preferred | 1 |
| Wholesale | 2 |

System price types have a `tier_level` below 100. You can rename them but never archive them. Retail is the company default.

A company can also define custom price types. A custom price type gets a `tier_level` of 100 or higher and a name that no other active price type uses. Creating one returns `422` with `catalog_writes_required` until the `custom_price_types` capability is on for the company. Send `copy_from_pricing_tier_id` to start the new price type from another price type's explicit prices.

Archiving a price type is the only way to remove it. If member types still point at it, name another active price type in `reassign_to_pricing_tier_id` to move them first. Each price type reports how many member types use it in `member_type_count`, and `archived_at` stays `null` while it is active.

[List company pricing tiers](/api-reference/members/list-company-pricing-tiers) returns the active price types in ascending `tier_level` order. Add `include_archived` to include archived ones. To change them, use [Create a custom price type](/api-reference/members/create-a-custom-price-type), [Rename a price type](/api-reference/members/rename-a-price-type) and [Archive a price type](/api-reference/members/archive-a-price-type).

## Member types

A member type classifies the people who buy from a company. Each member type points at one price type, and that link is what connects a buyer to a price.

Every company has three system member types:

| Member type | Slug | Price type | `rep_eligible` |
| --- | --- | --- | --- |
| Customer | `customer` | Retail | `false` |
| Preferred | `preferred` | Preferred | `false` |
| Rep | `rep` | Wholesale | `true` |

A member type with no price type reads back as `pricing_tier: null` and prices at Retail. A custom member type you create starts that way. You can't assign a custom price type to a member type yet.

When the charges rollout is on for the company, a cart charges the price type of the buyer's member type. An enrollment cart charges the price type of the member type the buyer enrolls into. A rep who holds a Preferred member type pays Preferred, because being a rep doesn't override the member type.

[List company member types](/api-reference/members/list-company-member-types) returns every member type, archived ones included, with its price type nested under `pricing_tier`. Use [Create a custom member type](/api-reference/members/create-a-custom-member-type) and [Update a member type](/api-reference/members/update-a-member-type) to change them.

## How a price resolves

Fluid prices a variant for one buyer in one country. The buyer's member type gives the price type. The country gives the market. These steps run in order, and the first one that yields a price wins:

1. **Market.** Fluid maps the country to its region and uses the market for that region. If the country or its region has no market, Fluid uses the company's first market by position. A company with no markets has no price.
2. **Catalog.** Fluid uses the market's catalog for the price type. If the price type has no catalog in that market, Fluid uses the market's base catalog, which holds the Retail prices.
3. **Price.** Fluid uses the explicit price stored for the variant in that catalog's price list. If there is none and the price list has a blanket adjustment, Fluid applies the adjustment to the base catalog's price. If there is neither, the variant has no price.

Prices are stored per variant, market and currency, not per country. Two countries in the same region share a market, so they share prices. Rows are sparse: a variant with no explicit price for a price type has no row, which isn't the same as a price of zero.

### Strict price types

Once the charges rollout is on for a company, Preferred and every custom price type are strict. A strict price type has no fallback. It needs its own catalog and an explicit price for the variant, and a blanket adjustment doesn't count. Retail and Wholesale keep the fallbacks above.

### Products, variants and bundles

A price belongs to a variant. A product with several variants has a price for each one.

A bundle has no variant to price, so it takes its price from one of two places. With bundle-level pricing on, the bundle has one fixed price per country. With it off, the bundle's price is built from the prices of its groups. The bundle price grid reports which applies in `pricing_enabled`.

### What unavailable means

A price is unavailable when no price exists for the buyer's price type in that country. Fluid doesn't invent a substitute, and it never reads a missing price as zero.

- A bundle is unavailable in a country when its fixed price has no enabled entry with a price for that country, or when any group with country pricing has no enabled entry for it.
- A cart line for a bundle that can't be priced for the buyer's price type sets `price_unavailable` to `true`, returns null price fields, and checkout refuses it.
- A cart line that a strict price type can't price is refused at payment with the `strict_tier_line_refused` code.

### Recurring prices

A recurring price can differ from the one-time price. It is stored apart from the one-time price, per price type, so a price row has a `subscription` field next to `one_time`.

- If no recurring price is stored for the variant, the recurring price follows the one-time price. The price row reports this as `follows_one_time`.
- If the subscription plan's `price_adjustment_type` is `percentage`, the recurring price is the one-time price less that percentage. It doesn't read a stored amount.
- If the plan is inactive, it grants no discount, so the recurring price is the one-time price.
- A blanket adjustment never prices a recurring price.

A bundle keeps its recurring price per price type and currency, and can override it per subscription plan in `plan_overrides`.

## The capabilities that gate it

Fluid turns member pricing on one company at a time. It isn't a setting you change in the company yourself. Fluid works out the answer from its rollout configuration each time it is asked, and reports it in a `member_pricing` object on the company record that Fluid Admin loads.

| Capability | Meaning when `true` |
| --- | --- |
| `catalog_reads` | Prices resolve through markets and catalogs. |
| `catalog_writes` | Price edits write the catalog directly, and the catalog price endpoints are available. |
| `custom_price_types` | The company can create custom price types. It currently mirrors `catalog_writes`. |
| `preferred_editable` | Preferred is the company's own price, not a copy of Retail. |
| `bundle_pricing` | Bundle prices are stored per price type, and the bundle price grid is available. |

The charges rollout, which makes carts charge a member type's price type, isn't one of these fields. It turns on together with reads, writes and `preferred_editable`, so ask Fluid whether it is on.

This is the capability object of the CrashTest Co. stage company. It reads from catalogs and writes to them, but Preferred is still a copy of Retail and the bundle price grid is off.

```json
{
  "member_pricing": {
    "catalog_reads": true,
    "catalog_writes": true,
    "custom_price_types": true,
    "preferred_editable": false,
    "bundle_pricing": false
  }
}
```

### When a capability is off

- **`catalog_reads` off.** Prices come from each variant's per-country retail and wholesale price columns. These can't express a Preferred or custom price type.
- **`catalog_writes` off.** The catalog price endpoints answer `422`, and creating a custom price type answers `422`.
- **`preferred_editable` off.** The Preferred price type holds the same prices as Retail, and Preferred members can't be charged a separate price.
- **`bundle_pricing` off.** The bundle price grid answers `422`, and a bundle is priced from its fixed price or its groups.
- **Charges off.** A member type's price type doesn't affect what a cart charges. A cart linked to a wholesale rep, and any enrollment cart, charges Wholesale. Every other cart charges Retail. Member-facing product pages show Wholesale to members whose member type is `rep_eligible` and Retail to everyone else, so the page matches the cart.
