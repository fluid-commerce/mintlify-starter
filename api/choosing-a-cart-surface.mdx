Fluid publishes two REST surfaces for carts:

- The **Checkout API** is for direct REST integrations.
- The **Public SDK API** is the contract behind the `@fluid-app` FairShare SDK.

They are two versioned front doors to the same cart engine. A cart token created
through either surface identifies the same cart on the other. The surfaces are
not aliases, however. Their operation names and request shapes differ, and
unsubscribing a bundle line through the wrong Checkout API operation leaves its
pricing behind.

Use one surface for each cart lifecycle. Follow the generated reference links
below for the current request and response contracts.

## Choose a surface

| If you are | Use | Why |
| --- | --- | --- |
| Building a new direct REST integration | **Checkout API** | It is the forward surface for direct integrations. It also owns customer accounts, subscription management, store configuration, cart points, and directory lookups. |
| Using the `@fluid-app` FairShare SDK | **Public SDK API** | This is the only REST contract the SDK registers. Its cart methods call this surface for you. |
| Building storefront widgets, tracking, media, or forms | **Public SDK API** | These browser-facing capabilities do not exist on the Checkout API. |
| Building enrollment-pack carts | **Public SDK API** | Enrollment-pack lookup and cart enrollment are unique to this surface. |
| Handling payment-gateway callbacks | **Public SDK API** or **Cart payment API** | The Checkout API does not own gateway callbacks. |

## Know which cart operations need a token

A shopper on your storefront has no account and no secret, and code that runs
in their browser can't keep one. So the cart doesn't ask for a Bearer token.
The `cart_token` that creating a cart returns is the credential instead: only
the browser or app that created the cart holds it, and it opens only that cart.

Anyone holding a cart token can shop with that cart. The operations that change
what the buyer pays, who gets credit for the sale, or whose saved data is on
the cart need a Bearer token as well.

### What the cart token alone allows

On both surfaces, a request with only the cart token can:

- Create a cart and add, change, subscribe, or remove line items.
- Set the buyer's email and phone, the address, and the shipping method.
- Apply or remove a promo code, and change the cart's country or language.
- Send and confirm a sign-in link, and sign the buyer out.
- Complete the cart.

On the Checkout API, the cart token also covers the email and SMS marketing
opt-ins and the automatic points setting.

### Fields the cart token can't change

Some fields are accepted in a request body but ignored when the request has no
token that allows them. The request still succeeds, so check the response
rather than assuming the value was applied.

| Field | Without the right token |
| --- | --- |
| A line item's `price` | Ignored, and the catalog price applies. The Checkout API never accepts a price override. On the Public SDK API, overrides belong to admin tooling. |
| `member_id` or `customer_id` when creating a cart | Ignored. Fluid sets the buyer from the browser session or from a sign-in link instead. |
| `source: "admin"` when creating a cart | Saved as `web`. |
| `member_type_id` on an enrollment cart (Checkout API) | Returns `401` with no token, and `403` for a token without the `members.manage` permission. Customer and member tokens can't set it. |
| `checkout_from_admin` and `legacy_customer_id` in cart metadata | Dropped. Only Fluid sets these, because they control the 3D Secure challenge and which customer the cart belongs to. Your other metadata keys are saved. |

### Operations that need a Bearer token

| Operation | Why it needs a token |
| --- | --- |
| [Apply a manual discount](/api-reference/cart-discount/apply-manual-discount-admin-only) | It changes the price, so it needs a signed-in user with permission to override orders. |
| [Set the volume rep](/api-reference/carts/set-volume-rep) | The rep assignment is recorded against the signed-in identity. |
| [Sync customer data](/api-reference/carts/sync-customer-data-to-cart) | It copies the signed-in customer's saved addresses and payment methods onto the cart. |
| Override line-item prices or volumes (Public SDK API) | Admin tooling uses these to adjust an order. |

A token for a different company never unlocks a cart. Keep company API tokens
on your server. Never send one from storefront code.

## Distinguish the two `v2025-06` APIs

Two unrelated APIs carry the same version label:

| Label | Surface |
| --- | --- |
| `/api/public/v2025-06/…` | The browser-facing **Public SDK API** described here. |
| `/api/v2025-06/…` | A separate admin and partner API. Its resources and authentication model are unrelated. |

The Public SDK API version names the specification, not one uniform path
prefix. Most operations use `/api/public/v2025-06/`. The same spec also owns
payment callbacks under `/api/v202506/carts/`, several unversioned public
utilities, and a cart price-override operation under `/api/carts/`. Use each
generated operation page as the source of truth for its exact path.

## Do not mix surfaces on a bundle cart

<Warning>
  Pick one surface for each cart lifecycle.

  On the Checkout API, subscribe and unsubscribe a line with the dedicated
  `subscription` operations, not by changing subscription fields with
  `PATCH items/{id}`. Unsubscribing a bundle line through the dedicated
  operation reprices the bundle's child items at one-time prices, as the Public
  SDK API does. Clearing the fields with `PATCH` does not reprice the children
  or release the subscription-derived price lock.

  Moving a bundle cart between surfaces, or between those two Checkout API
  operations, can leave child pricing in a state that neither path would have
  produced on its own.
</Warning>

## Understand the `stable` alias

`/api/public/stable/` is a live alias for the operations mounted from the same
public route set as `/api/public/v2025-06/`. The FairShare SDK uses the alias
for realtime authentication.

The alias is not blanket. The video-analytics operation uses a separate
versioned route and has no `stable` twin. The 18 operations in this
specification that sit outside `/api/public/v2025-06/` are also not rewritten
through the alias.

Use the explicit version when you need a pinned contract. Use `stable` only
when you deliberately want to follow the current Public SDK API version.
