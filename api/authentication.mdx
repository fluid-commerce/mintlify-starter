Company endpoints on the Fluid API are authenticated with a bearer token. Fluid provides three token types for integrators — company, partner, and public — each designed for a different trust level and integration pattern. Public storefront read endpoints require no token at all; everything below applies to the token-authenticated company surface.

## Passing your token

Include your token in the `Authorization` header, prefixed with `Bearer `:

```bash
curl https://api.fluid.app/api/v202604/company/products \
  -H "Authorization: Bearer <your_token>" \
  -H "Content-Type: application/json"
```

A request with a missing, invalid, expired, or revoked token receives a `401 Unauthorized`. The `401` body is a bare `{ "message": "..." }` object rather than the wrapped error envelope used by `404` and `422` responses — see [Errors](/api/overview#errors) for the full envelope contract.

## Token types

Each token type has a different scope of access and a different lifecycle.

### Company token

A company token grants full administrative access to your Fluid account, equivalent to a logged-in admin. Use company tokens for server-side integrations, internal tooling, and automation scripts where you fully control the runtime environment.

Create a company token from your Fluid dashboard under **Settings → API Tokens**. This is the primary way to obtain a company token. The same page is mirrored at **Developer Hub → API Tokens** if you work out of the Developer Hub.

<Warning>
  Never use a company token in client-side JavaScript or commit it to a public repository. Anyone who obtains a company token has full access to your account.
</Warning>

### Partner token

A partner token provides company-level access for third-party integrations. Partner tokens support an optional expiration and can be tied to a role, making them safer to distribute than a raw company token. They suit agency-built integrations, certified app partners, and automated workflows that need elevated access without sharing your primary company token.

### Public token

A public token is designed for client-side use and is scoped to a limited set of read and asset permissions, so it can be embedded in browser code or mobile apps. Every public token is prefixed with `pub-`, which makes it easy to spot one that has been committed where a private token belongs. Because a public token is exposed to end users, keep its access as narrow as your integration allows. See [Working with public tokens](#working-with-public-tokens) for how to create one and how to scope it.

<Note>
  Partner and public tokens can also be managed programmatically on the `/api/v2025-06/tokens/*` endpoints. A published API reference for token management is forthcoming.
</Note>

## Working with public tokens

### Create a public token

Go to **Settings → API Tokens** and create a token from the **Public Tokens** card. You give the token a name (unique within your company), select its scopes, choose an expiration, and optionally add domains to its allowlist.

The full token value is shown **once**, at creation. After that the dashboard lists only a masked form — `pub-` followed by the last eight characters — so copy the token somewhere safe before closing the dialog. If you lose it, create a replacement and delete the old one.

<Note>
  Creating a public token requires a company or partner token: a public token cannot mint another public token.
</Note>

### Expiration and the domain allowlist

A public token must carry **an expiration, a domain allowlist, or both**. A token that never expires and has an empty allowlist is rejected at creation.

The dashboard offers expirations of 1 hour, 24 hours, 7 days, 30 days, or **Never expires**. Picking **Never expires** requires at least one allowlisted domain.

Prefer a short expiration wherever you can mint tokens on demand: your server issues a fresh token for each page load or session, so a leaked one is useful only briefly.

### Scopes

A public token reaches only the endpoints its scopes cover. Grant the narrowest set your integration needs.

| Scope | Access |
| --- | --- |
| `dam:browse` | Browse and search existing assets |
| `dam:upload` | Upload files to the company DAM |
| `dam:unsplash` | Search Unsplash photos |
| `dam:ai_generate` | Generate images with AI |
| `media:read` | Read, index, and search media |
| `products:read` | Read, index, and search products |
| `enrollments:read` | Read, index, and search enrollments |
| `playlists:read` | Read, index, and search playlists |
| `forms:read` | Read, index, and search forms |

A [DAM Picker](/sdk/files-sdk) integration typically needs `dam:browse` and `dam:upload`, plus `dam:unsplash` for stock photography and `dam:ai_generate` for AI image generation.

## Storefront company permissions

The v2026-04 storefront company endpoints (`/api/v202604/company/...`) accept a company-admin bearer token carrying `storefront.view` for reads and `storefront.update` for writes.

## Best practices

- **Store tokens in environment variables.** Never hard-code tokens in source files. Use `.env` files locally and a secrets manager (such as AWS Secrets Manager or Vault) in production.
- **Use the least-privileged token type.** Prefer public tokens for client-side code, partner tokens for third-party integrations, and reserve company tokens for fully trusted server-side environments.
- **Prefer expiring tokens.** Even for long-running integrations, favor tokens that expire and are refreshed over indefinite ones.
- **Rotate and audit.** Periodically regenerate tokens, and review and revoke unused tokens under **Settings → API Tokens**.
