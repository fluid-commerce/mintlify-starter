Exigo accepts calls only from IP addresses each tenant has allowlisted. A Mist app runs on Vercel, where the outbound address changes, so no tenant can allowlist it. Fluid's egress proxy lends your app a fixed outbound address that Exigo tenants can allowlist.

The proxy only opens a tunnel. The TLS connection runs from your app to Exigo through it, so the proxy never sees your Exigo credentials or the data you exchange.

## What the proxy reaches

- **Exigo's REST API:** any subdomain of `exigo.com`, on port 443. The bare `exigo.com` host is refused.
- **Exigo-hosted SQL replicas:** port 1433, matched by the address the host name resolves to, not by the name itself. This covers Exigo's own networks and Exigo's shared Azure SQL server, including the aliases that point to it.

The proxy refuses every other host and port. Two consequences:

- A replica host name that doesn't resolve to one of Exigo's addresses is refused with a `403`.
- The proxy refuses IP addresses as destinations. Connect to a host name and a port.

## Before you start

- Your Mist app has a droplet attached. See [Integration points](/mist-apps/integration-points).
- You're an admin of the company that owns the droplet, or you use a company service token of that company.
- The Exigo tenant has allowlisted all four of Fluid's egress addresses, for both the API and the SQL replica:

  | Address | Used |
  | --- | --- |
  | `34.59.103.199` | Now |
  | `34.171.199.225` | Now |
  | `34.144.173.17` | After the proxy moves to its new region |
  | `34.174.57.210` | After the proxy moves to its new region |

  Fluid is moving the proxy to a new region, and the move has no date yet. Until it moves, Exigo sees only the first two addresses. Allowlist all four now, so calls keep working through the move. Fluid will update this page when the first two can be removed.

## Turn on the egress proxy

Turn it on with any of these:

- **CLI, on an existing app:** run `fluid mist droplet egress-proxy on` from the app's folder, or pass the app's slug: `fluid mist droplet egress-proxy on spring-bonus`.
- **CLI, when you add the droplet:** add `--egress-proxy` to `fluid mist create` with a droplet, or to `fluid mist attach --kind droplet`.
- **Mist:** check the egress option when you add or edit the droplet in the integration point dialog. The option shows when your company has it.
- **Admin:** open the droplet's settings, and under **Network Access**, check **Let this droplet reach external systems (e.g. Exigo) through Fluid's egress proxy**.

The proxy lets the droplet through once egress is on, with no further approval. To turn it off, run `fluid mist droplet egress-proxy off`, or uncheck the option.

Only an admin of the company that owns the droplet, or a company service token of that company, can turn egress on. For anyone else, the API refuses the change. The CLI's `--egress-proxy` adds the droplet without egress and prints a warning. Admin and Mist don't show the option.

### How long a change takes

The proxy keeps each droplet's answer for a short time:

- After you turn egress on, new connections can still be refused for up to a minute.
- After you turn egress off, new connections are refused within a minute.

In both cases, if the proxy can't reach Fluid, it keeps using its last answer for up to five more minutes.

Connections that are already open keep running until they close.

## Use the proxy from your app

Fluid sets `FLUID_EGRESS_PROXY_URL` on your app when you add a droplet, in environments that have an egress proxy. The variable is set whether egress is on or not, so it doesn't mean egress is on: until it is, the proxy answers `403`. A Mist app whose droplet was added before the proxy existed doesn't have the variable. Add the droplet again to get it.

Your app authenticates to the proxy with the installation's droplet installation token, which starts with `dit_`. See [Authentication](/mist-apps/authentication#the-droplet-install-flow) for where the token comes from.

With the [Exigo connection SDK](/sdk/exigo-sdk), pass both to the REST client and the SQL pool:

```ts
import { createExigoRestClient } from "@fluid-app/exigo-connection-sdk/rest";
import { getExigoPool } from "@fluid-app/exigo-connection-sdk/sql";
import { resolveFluidInstallation } from "@/lib/fluid/installation-context";
// Defined once per app: see the SDK's "Define the credentials".
import { resolveExigoCredentials } from "@/lib/exigo";

// Authorize the caller first. See the warning below.
const { installation, companyId } = await resolveFluidInstallation(request);
const { rest, sql } = await resolveExigoCredentials(String(companyId));

const egressProxy = process.env.FLUID_EGRESS_PROXY_URL
  ? {
      url: process.env.FLUID_EGRESS_PROXY_URL,
      token: installation.authenticationToken,
    }
  : undefined;

const exigo = createExigoRestClient(rest, { egressProxy });
const pool = await getExigoPool(sql, { egressProxy });
```

<Warning>
  `resolveFluidInstallation` finds the installation from the `x-fluid-droplet-installation` header. It doesn't authenticate whoever sent the request. Before a route loads a company's Exigo credentials, check that the caller may act for that company, for example with a [session token](/mist-apps/authentication#viewer-identity-with-session-tokens).
</Warning>

Without the SDK, use any HTTP client that supports an HTTPS `CONNECT` proxy, and send the token on the proxy request:

```http
Proxy-Authorization: Bearer dit_9XcT3vMq7LpW2nRb5KsZ8hJf
```

The proxy URL is always `https`, because the token travels outside the tunnel.

### Local runs

`fluid mist env pull` doesn't include `FLUID_EGRESS_PROXY_URL`, so a local run calls Exigo directly from your own IP address. The code above does that when the variable isn't set. To test the proxied path, deploy the app.

## When the proxy refuses

The Exigo connection SDK throws `ExigoProxyError`, whose `status` is the proxy's answer:

| Status | Meaning | What to do |
| --- | --- | --- |
| `407` | The proxy doesn't accept the token. | Send the installation's `dit_` token. The installation must still be active. |
| `403` | The proxy doesn't let this droplet or this host through. | Turn on the egress proxy for the droplet, and check that the host is one [the proxy reaches](#what-the-proxy-reaches). |
| `502` or `504` | The proxy couldn't reach the host. | Check the host name and port. |
| `503` | The proxy couldn't verify the token, is at capacity, or is limiting your rate of connections. | Retry after a short wait. |

### A 403 on an Exigo call that redirects

The proxy reaches `exigo.com` hosts on port 443 only. If a call follows a redirect to `http://`, the client opens a new tunnel to port 80, and the proxy refuses it with a `403`, even though the droplet is allowed and the same host works on 443. With `undici` or `fetch`, the error reads `Proxy response (403) !== 200 when HTTP Tunneling`.

The bare API root redirects this way: a `GET` on `https://…exigo.com/3.0` answers with a redirect to `http://`. To check a connection, call a real API endpoint, as the [Exigo connection SDK](/sdk/exigo-sdk) does, for example `GET /3.0/customers?customerID=0`. If you call Exigo with `fetch` yourself, pass `redirect: "manual"` so a redirect is reported instead of followed.

If the proxy lets you through but Exigo still refuses the call, one common cause is that the Exigo tenant hasn't allowlisted [Fluid's egress addresses](#before-you-start) for that service. The API and the SQL replica are allowlisted separately. Wrong Exigo credentials look similar: the SDK throws `ExigoAuthError`.
