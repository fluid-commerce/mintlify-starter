A checkout form collects extra information from a shopper who is enrolling, such as a date of birth, a tax ID or a signed document. Fluid shows it **after** the payment is taken and the order is placed, so it never adds a step between the shopper and paying. This guide explains the model end to end, then shows how a custom checkout reads and answers the form through the Checkout API.

<Info>
  Merchants build forms in the admin. For the screen-by-screen steps, see
  [Forms](/help/admin/forms) in the Help Center. This guide covers the model
  and the API.
</Info>

## The model

| Piece | What it is |
| --- | --- |
| **Form** | A set of fields you build in the admin, with a title, a form type, a list of countries and an **Active** switch |
| **Form type** | **Post Purchase** forms appear at enrollment checkout. **General** forms are standalone forms shared by link or embed. **Pre Purchase** is retired and can't be chosen for new forms |
| **Field** | One question, such as **Date of Birth** or **File Upload**, with a label and a **Required** switch |
| **Countries** | The cart countries a form applies to |
| **Enrollment** | Created for each enrollment cart. It carries the token that addresses its fields, and its state is complete or incomplete |
| **Answer** | A shopper's saved response to one field, stored as text. A file answer is stored as a link to the uploaded file |

### Which carts get a form

Forms apply only to **enrollment carts**. A cart becomes one when the shopper adds an enrollment pack, or when it's flagged with [Flag a cart as enrollment eligible](/api-reference/carts/flag-a-cart-as-enrollment-eligible). A regular cart never gets a form.

An enrollment cart gets every form that is **Post Purchase**, **Active**, and set to the cart's country. Forms aren't attached to enrollment packs, member types or products, so every enrollment in a country gets the same fields. When more than one form matches, checkout shows their fields together as one form.

### When the form appears

<Steps>
  <Step title="Checkout places the order">
    The shopper pays. Checkout captures the payment and places the order. Outstanding form fields never block this step.
  </Step>
  <Step title="The order confirmation page shows the form">
    Fluid-hosted checkout renders the form at the top of the order confirmation page, above the order-details drop zones. It appears only when the order has an enrollment and the enrollment has outstanding Post Purchase fields.
  </Step>
  <Step title="The shopper submits">
    Checkout saves each answer. File fields upload as soon as a file is dropped in.
  </Step>
  <Step title="The enrollment completes">
    When every required field has an answer, the enrollment is complete. Fluid saves a copy of the answers with the new member's record and sends the enrollment completed webhook.
  </Step>
</Steps>

### What the order and the form each decide

The **order** decides the purchase and the membership. The shopper is charged, the order exists, and the shopper is enrolled as a member of the enrollment's member type as soon as checkout places the order, whether or not they ever open the form.

The **form** decides only whether the enrollment is complete. An incomplete enrollment means:

- The form keeps appearing on the order confirmation page, with saved answers filled in.
- Fluid emails up to five reminders over about 25 days, each linking back to that page, while the company's enrollment completion reminder email is active.
- The enrollment completed webhook hasn't fired yet.

Only fields marked **Required** keep an enrollment open. A form whose fields are all optional doesn't.

## Read and answer the form through the API

Fluid-hosted checkout does all of this for you. Use these steps when you build your own order confirmation experience on the Checkout API, or when an agent or back-office tool collects the answers instead.

<Steps>
  <Step title="Get the enrollment token">
    [Complete checkout](/api-reference/carts/complete-checkout) returns the new order. On an enrollment order, its `enrollment_token` addresses the enrollment. You can read it again later from [Show order](/api-reference/orders/show-order). On a regular order, it's null.
  </Step>
  <Step title="Read the fields">
    Call [Show enrollment](/api-reference/enrollments/show-enrollment) with the token. It needs no Bearer token: the enrollment token is the credential, so treat it like a password. The response lists `enrollment_fields`, each with its type, order, placement, any saved answer, and its builder settings, plus the enrollment's `state`.

    Render only fields whose `placement` is `post_purchase`. That's what Fluid-hosted checkout shows. The list can also carry fields from other active forms for the country.
  </Step>
  <Step title="Save each answer">
    Send each answer with [Submit enrollment field answer](/api-reference/enrollments/submit-enrollment-field-answer). The answer is a string, so send a date as `1985-04-12` and a yes-or-no answer as text.

    For a file field, send the file with [Upload file for enrollment field](/api-reference/enrollments/upload-file-for-enrollment-field). Fluid accepts JPEG, PNG, WebP, TIFF or PDF files up to 5 MB.
  </Step>
  <Step title="Change a saved answer">
    Use [Update enrollment field answer](/api-reference/enrollments/update-enrollment-field-answer) with the field's `id` in the path, the same ID you submitted the answer with. It changes the field's latest saved answer. A field with no saved answer yet returns `404`, so submit its first answer instead. Submitting a second answer for the same field creates another answer instead of replacing the first.
  </Step>
  <Step title="Check completion">
    Read Show enrollment again. When `state` is `complete`, the enrollment is finished. After that, every write to the enrollment is refused with `422`.
  </Step>
</Steps>

<Warning>
  Checkout checks only that required fields are filled in. Fluid saves any
  string as an answer, so validate formats, such as a tax ID's length, in your
  own front end before you submit.
</Warning>

### Webhooks

Subscribe to these with the [Webhooks guide](/api/guides/webhooks). Call [List webhook resources](/api-reference/webhooks-resources/list-webhook-resources) for the exact resource and event pairs your company can use.

| Event | When it fires |
| --- | --- |
| `enrollment_started` | When Fluid creates the enrollment for an enrollment cart |
| `form_submitted` | When an enrollment saves its first answer to a form. It doesn't mean the form is finished |
| `enrollment_completed` | When every required field has an answer |

To act on finished enrollments, such as sending a welcome kit or syncing to a compensation system, use `enrollment_completed`. Don't use `form_submitted` for that.

### Managing forms

Build and edit forms, and read or export all of a form's responses, in the admin. See [Forms](/help/admin/forms). You can also manage forms through the API, as [Build a form through the API](#build-a-form-through-the-api) shows. Through the Checkout API you can read and answer one enrollment's fields at a time, by its token.

## Build a form through the API

Use the Forms API when a script or an agent sets up forms, for example while you [open a country](/setup/open-a-country). Every request takes a company Bearer token. Reading needs the forms view permission, and writing needs the forms update permission. The steps below build Dunder Mifflin's form for Germany. Each operation's reference page holds its full parameters and responses.

### Find the country's ID

A form's `country_ids` takes Fluid's ID for each country. Read it from [List company countries](/api-reference/countries/list-company-countries): use the entry's `country.id`, not the entry's own `id`, which identifies your company's settings for the country.

```bash
curl "https://api.fluid.app/api/settings/company_countries" \
  -H "Authorization: Bearer <token>" \
  | jq '.company_countries[] | select(.country.iso == "DE") | .country.id'
```

This prints `74`, Germany's ID. A country you haven't opened isn't in that list. Find it in [List countries](/api-reference/company-v0/countries/list-countries), which returns Fluid's whole country catalog.

### Write the fields

Each field is a component: an object with an `element_type` and its settings. [List form elements](/api-reference/form-elements/list-form-elements) describes every element type. Dunder Mifflin saves the German fields in `enrollment-germany.json`:

```json enrollment-germany.json
[
  {
    "element_type": "input",
    "puck_type": "legal_name",
    "label": "Full legal name",
    "required": true,
    "sensitive_info": false,
    "is_form_field": true
  },
  {
    "element_type": "short_text_entry",
    "label": "Tax number (Steuernummer)",
    "placeholder": "21/815/08150",
    "required": true,
    "sensitive_info": true,
    "is_form_field": true
  },
  {
    "element_type": "file_upload",
    "label": "Trade registration (Gewerbeanmeldung)",
    "required": true,
    "sensitive_info": false,
    "is_form_field": true
  },
  {
    "element_type": "multiple_choice_entry",
    "label": "How did you hear about us?",
    "multiple_choice_options": [
      { "label": "Social media" },
      { "label": "A friend or family member" },
      { "label": "A rep" },
      { "label": "Search" },
      { "label": "An event" },
      { "label": "Other" }
    ],
    "required": false,
    "sensitive_info": false,
    "is_form_field": true
  }
]
```

- Set `is_form_field` to `true` on every component that collects an answer. Without it, the element isn't an enrollment field: checkout doesn't ask for it, and it never holds an enrollment open.
- An identity field is an `input` whose `puck_type` names it, such as `legal_name`, `email` or `date_of_birth`.
- Use `short_text_entry` for a tax ID outside the United States. Checkout formats the `ssn` identity field as a US Social Security number.
- Fields appear in the order you list them.

### Create the form as a draft

`form_components` is a JSON-encoded string, not an array. Let `jq` encode the file into the request body:

```bash
jq -n --arg components "$(jq -c . enrollment-germany.json)" '{
  form: {
    title: "Enrollment - Germany",
    form_type: "post_purchase",
    status: "draft",
    country_ids: [74],
    form_components: $components
  }
}' > create-form.json

curl -X POST "https://api.fluid.app/api/forms" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: enrollment-germany-2026-10" \
  --data @create-form.json
```

In the body `jq` writes, the components are one escaped string:

```json create-form.json
{
  "form": {
    "title": "Enrollment - Germany",
    "form_type": "post_purchase",
    "status": "draft",
    "country_ids": [74],
    "form_components": "[{\"element_type\":\"input\",\"puck_type\":\"legal_name\",\"label\":\"Full legal name\",\"required\":true,\"sensitive_info\":false,\"is_form_field\":true},{\"element_type\":\"short_text_entry\",...}]"
  }
}
```

- Send the fields inside the `form` object. The API reads nothing outside it.
- Set `form_type` to `post_purchase` for a form checkout shows. `general` makes a standalone form. `pre_purchase` is retired and returns `422`.
- A new form is a `draft` unless you set `status`, so no enrollee sees it while you check it.
- Marking a field `sensitive_info` needs the forms manage-sensitive permission. Without it, the request returns `422` and creates nothing.
- The `Idempotency-Key` header makes a retry safe. The same request with the same key returns the form the first request created.

The response returns the form with its `id`, here `5821`. Its `form_components` carry each element's `id`. Save the response as `form.json`; you need those IDs to change the fields later.

### Activate it

Send only what changes. A request without `form_components` leaves the fields as they are.

```bash
curl -X PUT "https://api.fluid.app/api/forms/5821" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"form": {"status": "active"}}'
```

Enrollment checkouts in Germany now show the form after payment.

### One form per country, or one form for several

Checkout shows every active Post Purchase form for the cart's country, combined into one form. Overlapping forms all show. Use this rule of thumb:

- **Shared fields: one form across countries.** Questions every market asks the same way can live on one form whose `country_ids` lists each country.
- **Country-specific legal or tax fields: one form per country.** A German tax number on a form shared with the United States would ask American enrollees for it too.
- **Ask each question once.** If a shared form and a country's own form both ask how the enrollee heard about you, enrollees in that country see the question twice. The same goes for Fluid's generic enrollment form for a country, which opening the country can add. See [Open a country](/setup/open-a-country).

To add a country to an existing form, send the whole list, because `country_ids` replaces the form's countries. Read the current ones from the form's `countries`. Dunder Mifflin's `Rep preferences` form asks for product interests and a contact preference in the United States (`214`) and Canada (`35`). This adds Germany:

```bash
curl -X PUT "https://api.fluid.app/api/forms/5790" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"form": {"country_ids": [214, 35, 74]}}'
```

### Change fields without dropping any

`form_components` in an update is the form's whole new layout:

- A component with the `id` of one of the form's elements updates that element in place, and its answers stay with it.
- A component without an `id` adds a new element.
- An element you leave out is deactivated. Its answers are kept, but checkout stops asking for it.

Start from the form's current `form_components`, which carry their IDs. Every create and update response returns them, and so does [List forms](/api-reference/forms/list-forms). Don't rebuild them from [List form elements](/api-reference/form-elements/list-form-elements): it also lists elements that earlier edits deactivated.

This adds a date of birth to the German form and keeps every existing field:

```bash
jq '.form.form_components | fromjson' form.json > current.json

jq -n --arg components "$(jq -c '. + [{
  "element_type": "input",
  "puck_type": "date_of_birth",
  "label": "Date of birth",
  "required": true,
  "sensitive_info": false,
  "is_form_field": true
}]' current.json)" '{form: {form_components: $components}}' > update-form.json

curl -X PUT "https://api.fluid.app/api/forms/5821" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  --data @update-form.json
```

<Warning>
  Never send only the new field. Every component you leave out is
  deactivated, so the form would ask for nothing else. Sending an existing
  sensitive field without its `id` also counts as marking a new field
  sensitive, which needs the forms manage-sensitive permission.
</Warning>

### Follow up on responses

```bash
curl "https://api.fluid.app/api/forms/5821/incomplete_enrollees" \
  -H "Authorization: Bearer <token>"

curl -X POST "https://api.fluid.app/api/forms/5821/send_reminders" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"enrollment_ids": [90412, 90418]}'

curl -X POST "https://api.fluid.app/api/forms/5821/export_csv?include_sensitive=true" \
  -H "Authorization: Bearer <token>"
```

- [List form respondents](/api-reference/forms/list-form-respondents) returns each submission with its answers. Sensitive answers read `********` unless your token holds the forms view-sensitive permission.
- [List incomplete enrollees](/api-reference/forms/list-incomplete-enrollees) lists who still owes this form, and whether a reminder would go to them now.
- [Send manual enrollment reminders](/api-reference/forms/send-manual-enrollment-reminders) emails the eligible ones. Send `enrollment_ids` to remind only some. Each enrollee gets at most one manual reminder per 24 hours, counting automatic reminders.
- [Export form responses as CSV](/api-reference/forms/export-form-responses-as-csv) returns a download URL. `include_sensitive=true` unmasks sensitive answers only for a token with the forms view-sensitive permission.

Manual reminders are turned on per company. Without them, both reminder operations return `404`. Both return `422` for a form that isn't Post Purchase.

## Example: a rep enrollment form for the United States

Dunder Mifflin enrolls paper sales reps in the United States. It needs each new rep's legal name, date of birth and a signed W-9 to pay commissions.

| Field | Component | Required | Sensitive Info |
| --- | --- | --- | --- |
| Legal name | **Legal Name** | Yes | Off |
| Date of birth | **Date of Birth** | Yes | On |
| Blank W-9 | **File Download** | No | Off |
| Signed W-9 | **File Upload** | Yes | On |
| How did you hear about Dunder Mifflin? | **Multiple Choice** | No | Off |

The form is `Enrollment - United States`, with **Form type** set to **Post Purchase**, **Countries** set to United States, and **Active** on.

When Pam Beesly buys the Paper Sales Starter Kit from Dwight Schrute's link:

1. She pays on one page with no extra fields. Her order is placed, Dwight gets credit for it, and Pam becomes a member of the enrollment pack's member type.
2. The order confirmation page asks for her legal name, date of birth and signed W-9, and the optional survey question.
3. She uploads her W-9 the next day from the reminder email's link. The enrollment completes, and the enrollment completed webhook tells the company's compensation system to start paying her commissions.

For Canada, Dunder Mifflin adds a second Post Purchase form, `Enrollment - Canada`, set to Canada only. It asks for a SIN in a **Short Text Entry** field, with **Sensitive Info** on, instead of the W-9.

**Do it through the API:** [Build a form through the API](#build-a-form-through-the-api) creates the German form with the same requests. For these forms, change the title, the country's ID and the components.

## Example: "How did you hear about us?"

To learn where new members come from, add one optional **Multiple Choice** field to each country's Post Purchase form:

- **Label**: How did you hear about us?
- **Options**: Social media, A friend or family member, A rep, Search, An event, Other
- **Required**: off, so the question never holds an enrollment open

Read the answers in the form's responses in the admin, or export them as CSV.

**Do it through the API:** the question is the last component in [Write the fields](#write-the-fields). To add it to a form that's already live, follow [Change fields without dropping any](#change-fields-without-dropping-any).

A Post Purchase form reaches new members only, because regular checkouts never show forms. To survey every customer, use a **General** form and share its link, for example in a post-purchase email.

## Recommended field sets

### Enrollment

| Need | Component | Required | Notes |
| --- | --- | --- | --- |
| Legal name | **Legal Name** | Yes | Match tax and payout records |
| Date of birth | **Date of Birth** | Where you have an age minimum | Nothing checks the age for you |
| Tax ID | **Short Text Entry**, or **Social Security Number** in the US | Where you pay commissions | Turn on **Sensitive Info** |
| Tax or compliance document | **File Download** and **File Upload** | Where required | One field offers the blank document, the other collects the signed copy |
| Business details | **Short Text Entry** | No | For members who enroll as a business |
| Consent statement | **Checkbox** | Yes | Checkout shows only the label, so put the full statement in it |

For terms and policies the shopper must accept before buying, use [Agreements](/help/admin/settings/agreements), not a form field. Agreements linked to an enrollment appear in checkout before the order is placed, and each acceptance is recorded.

### Attribution and preferences

| Need | Component | Required |
| --- | --- | --- |
| How did you hear about us? | **Multiple Choice** | No |
| Product interests | **Multiple Choice** | No |
| Contact preference | **Multiple Choice** | No |
| Anything else? | **Long Text Entry** | No |

## Gotchas

- **Forms are country-scoped, not pack-scoped.** You can't show a different form for each enrollment pack or member type. Use one form per country when countries need different fields.
- **A form must be Active and Post Purchase.** A draft, or a General form, never appears at checkout.
- **General forms can hold enrollments open.** Completion counts the fields of every active form for the cart's country, but checkout shows only Post Purchase fields. Keep General forms out of the countries where you enroll members, or turn them off when you don't need them.
- **Pre Purchase forms are retired.** An older form with that type still asks before payment. Change it to Post Purchase.
- **A sponsor field doesn't set a sponsor.** Answers are stored as text. They don't change who gets credit for the order or the new member's sponsor.
- **No conditional logic and no pattern checks.** Every field shows to every shopper who gets the form.
