You publish a Site with the Fluid CLI. `fluid sites publish` saves your folder to the Site's source repository, uploads your build output and declarations, and makes them the Site's current version in one step. Until that step succeeds, the Site keeps serving its current version.

`fluid deploy` wraps the whole path for a project folder: it builds, creates the Site the first time, and publishes. Mist's **Publish** button and the [Fluid MCP server](/sites/deploy-from-claude) publish the same way.

For a direct API integration, see [Sites APIs](/api/member-sites).

## Before you start

Install the Fluid CLI and its Sites plugin, and sign in. The CLI needs Node.js 24 or later, and Git to save the Site's source:

```bash
npm install -g @fluid-app/fluid-cli @fluid-app/fluid-cli-member-site
fluid login
```

Your login follows the Site's owner. A member's Site is published with that member's login, and a company Site with the login of an admin who may change themes. With Sites plugin 0.1.427 or later, a company admin can also pull, publish and share a member's Site with `--as admin`. Say which one you're using with `--as member` or `--as admin`. Without it, the server decides and a refusal names the login the Site needs. Writes act as a person: a company API token can read company Sites but can't create or publish one.

`fluid sites publish` needs the folder's binding file, `.member-site.json`, which names the Site. Don't edit it or copy it into another Site's folder. To bind a folder to a new Site, run `fluid sites create` in it. It creates the Site and writes the binding there, and leaves your files alone:

```bash
fluid sites create diamond-leaders --name "Diamond Leaders" --as member
fluid sites create fall-launch --company --as admin
```

`--company` creates a company Site and needs an admin login. A folder already bound to the same Site is left as it is, and a folder bound to another Site is refused. To work on a Site whose source is already saved, clone it with [`fluid sites pull`](/sites/source-and-branches#pull-a-sites-source) instead.

## Deploy in one step

`fluid deploy` takes a project folder to a live address:

```bash
fluid deploy
fluid deploy --public
```

It reads what built the project (Vite, Astro, a Next.js static export or plain HTML), builds it with the project's own package manager, creates and binds a Site the first time, publishes with `fluid sites publish`'s own code, and prints the address. The first deploy asks once whether the Site is public. `--public` answers yes, and without a terminal the Site stays private. `--no-source` and `--as` work as they do for `fluid sites publish`.

A Next.js app with a server isn't a Site. `fluid deploy` explains why, with Fluid's recommendation when the server gives one, and creates nothing. See [Site or App?](/sites/site-or-app) and the [framework guides](/sites/frameworks/vite).

### Media in the Fluid DAM

Put a Site's images, video, audio and large fonts under `public/media/`, and reference them by path, such as `/media/hero.mp4`. Before it builds a Vite project, `fluid deploy` runs `fluid sites media sync`. That command uploads each new or changed file to your company's Fluid DAM and records its address in `config/media.json`. Commit that file. `fluidSite()` then points each reference at the DAM and leaves the file out of the build. `--no-media` skips the sync.

Only an admin login can upload to the DAM. With a member login, the media stays in the build, and the deploy says so.

<Warning>
  A file in the DAM is public to anyone who has its address, even when the Site is private. Keep a file that must stay private out of `public/media/`.
</Warning>

## Check the site

`fluid sites lint` checks the site's folder on your machine. It makes no request and needs no login.

```bash
npm run build
fluid sites lint
```

It runs the same checks `fluid sites publish` runs before it sends anything:

- Every file of the build has a type a site may serve, such as HTML, CSS, JavaScript, JSON, SVG, images, fonts, text, XML, PDF, MP4, WebM and MP3.
- No file is under `/_fluid/`, and nothing in the build is a symbolic link.
- The build holds at most 2,000 files, each at most 25 MiB, and 250 MiB in all.
- The build has an `index.html` when there's no `config/routes.json`, and every route names a file of the build.
- `db/schema.json`, `config/access.json`, `config/meta.json` and `config/routes.json` are valid JSON and pass their rules.
- Every file at the top of `functions/` is a [server function](/sites/functions) that `config/functions.json` names, and every function it names has a file. Each function builds, with its imports, into an ES module of at most 10 MiB with a default export and no Node built-in module. `config/functions.json` passes its rules, and no build file is under `/api/` when the site has functions.

Each problem is an error that names its file. A clean folder prints nothing and exits `0`. Any error exits `1`.

For a company Site, `fluid sites lint` also warns when `config/meta.json` gives no title or description, or the build has no routes and no prerender entry. A warning doesn't stop a publish, and the title and description warning is fine when the Site's SEO settings set them. See [SEO and indexing](/sites/seo).

The build's folder is `dist` by default. Name another with `--dir`, relative to the site's folder:

```bash
fluid sites lint ./diamond-leaders --dir build
```

## Publish

```bash
fluid sites publish
fluid sites publish ./diamond-leaders --dir build --as member
```

The command:

1. Hashes every file of the build. A file under `assets/` whose name carries a content hash, such as `index-Bx3zQw9a.js`, is cached by browsers for a year.
2. Reads `db/schema.json` and the files in `config/`, and builds each [server function](/sites/functions) in `functions/`.
3. Runs the checks of `fluid sites lint`, and stops before any request when one fails.
4. Commits the folder and pushes it to the Site's source repository. See [Source in git](/sites/source-and-branches#source-in-git).
5. Uploads only the files the Site doesn't store yet. Publishing the same build twice uploads nothing the second time, and changing one file uploads one file.
6. Publishes: applies the schema, creating the Site's database on the first publish that has a `db/schema.json`, deploys the server functions, and makes the new build the Site's current version. It prints the Site's address.

| Option | What it does |
| --- | --- |
| `--dir <dir>` | The build's folder, relative to the Site's folder. The default is `dist`. A plain HTML Site with no build publishes from its own folder |
| `--as <login>` | `member` or `admin` |
| `--branch <slug>` | Publishes to the Site's [branch](/sites/source-and-branches#branches) instead of the Site itself |
| `--no-source` | Publishes without committing and pushing the folder first |
| `--remove-functions` | Publishes a folder with no `config/functions.json` even though the live Site runs server functions, and removes them |
| `--json` | Prints the result as one JSON object on stdout, and the progress on stderr |
| `--confirm <id>` | Confirms a destructive migration of `db/schema.json`. Repeat it for each one |
| `--finish-pending`, `--confirm-pending <id>` | Finish an earlier publish's schema change. See below |

A plain HTML Site has an `index.html` at the top of its folder, no `dist/index.html`, and no build script in `package.json`. With Sites plugin 0.1.353 or later, `fluid sites publish` publishes it from its own folder, the same files `fluid deploy` would. It leaves out `config/`, `db/`, `functions/`, `node_modules/`, `package.json`, `dist/`, every name that starts with a dot, and files a Site can't serve, and prints a line that names what it left out. From Sites plugin 0.1.411, Markdown files are served, except the `README.md`, `AGENTS.md` and `CLAUDE.md` at the top of the folder. It still reads `config/` and `db/schema.json` as it does for a built Site.

With `--json`, a successful publish prints `ok`, `site`, `bundle`, `manifestSha256`, `source` (the repository, branch and commit, or `null` when the source wasn't saved) and, when the server sends one, `url`.

A new Site is private until its owner makes it public. Publish it, open it at its address, and check it before you share it.

To go back to an earlier build, see [Deployments and rollback](/sites/deployments). The operations behind publishing are [Start a bundle upload](/api-reference/site-bundles/start-a-bundle-upload) and [Publish a bundle](/api-reference/site-bundles/publish-a-bundle), or for a company Site [Publish a company site's bundle](/api-reference/member-site-bundles/publish-a-company-sites-bundle).

### Make a Site public or private

`fluid sites visibility` sets who may open the folder's Site:

```bash
fluid sites visibility public
fluid sites visibility private ./diamond-leaders --as member
```

`public` lets anyone open the site, and `private` only the people it's shared with. Use the owner's login: `--as member` for your own site, `--as admin` for a company site. Whatever its visibility, a draft or a site a company admin took down opens for nobody, and a site a company admin locked opens only for company admins. The command says so. See [Share a Site](/sites/overview#share-a-site).

### Confirm a destructive schema change

A change to `db/schema.json` that drops, renames or retypes a table or column, or makes a column required, needs a migration. Confirm each migration by its id, once per migration:

```bash
fluid sites publish --confirm 2026-11-20-rsvp-party-size
```

Without it, the publish is refused with `destructive_change_unconfirmed`, the command lists each unconfirmed migration with its steps, and nothing changes. See [Change the schema](/sites/database#change-the-schema).

### Finish an interrupted schema change

If a publish leaves a schema change pending, the next publish offers to finish that bundle first. With no terminal, use:

```bash
fluid sites publish --finish-pending
```

That run finishes the pending bundle and stops. Run the command again for your own build. If the pending bundle needs destructive migration confirmations, check its schema and pass `--confirm-pending <id>` for each of its migrations. Your build's `--confirm` values are never applied to the pending bundle. See [Finish an interrupted publish](/sites/database#finish-an-interrupted-publish).

## What the answers mean

| Answer | What it means | What to do |
| --- | --- | --- |
| `404` on the start | The Site wasn't found for this login, or Sites aren't on for your company. Both answer the same `404` | Check the folder's `.member-site.json` and your login. If they're right, ask Fluid to turn Sites on |
| `409` `uploads_in_progress` | The site has 5 uploads in progress | Run it again once one finishes or expires, 60 minutes after it started |
| `409` on the publish | The bundle can no longer be published. Nothing changed | Run the command again for a new bundle |
| `422` | A check failed. The command names it and where, or the files that weren't stored. Nothing was published | Fix it and publish again |
| `422` `no_database` | The database is unavailable. Nothing was published | If it stays unavailable, [contact support](/help/getting-help) |
| `422` `functions_api_path_taken` | The site has server functions and its build has a file under `/api/`, where they answer. The answer names the file | Move the file out of `/api/` |
| `422` `functions_not_available` | This Fluid environment doesn't run server functions. Nothing was published | Publish without `functions/`, or [contact support](/help/getting-help) |
| `409` `copy_in_progress` | A copied Site's files, or a branch's database, are still being copied. Nothing was published | Wait for the copy, then run the command again |
| `409` `schema_change_pending` | An earlier publish's schema change timed out and may have run. Nothing from this build was published | Publish the version the answer names (`details.pendingBundle`) again. That finishes the change. On a terminal, the command offers to do it. Elsewhere, run it again with `--finish-pending`. Then publish your build again |
| `422` `destructive_change_unconfirmed` | The schema has a destructive change you didn't confirm | Run it again with `--confirm` for each migration listed |
| `502` | Fluid couldn't finish a step, and the bundle failed | Run it again |
| `504` `publish_timeout` | The publish ran out of time. The current version keeps serving | Nothing: the command tries the publish up to three times in all. After that, run the same command again. It's safe, and uploads no file again |
| `504` with no code | A proxy timed out, so the outcome is unknown and the build may still go live | Wait a minute, check what the site shows, then run it again without rebuilding |

When Fluid can't set up the Site's source repository, the command says so and publishes without the source. A later publish saves it.

The command never prints the upload addresses it uses.
