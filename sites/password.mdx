A public Site can ask visitors for a password before it opens. Anyone who has the address and the password can open it, signed in or not. Use it to share a page with people outside your company's member list, such as event guests, without opening it to everyone. To set one, see [Set, change or remove the password](#set-change-or-remove-the-password).

## Who is asked for the password

The Site's owner and company admins aren't asked. Everyone else is, members the Site is shared with included.

A password Site is public, so a share gives its holders nothing a visitor with the password doesn't have. While a Site has a password:

- Shares that can edit open nothing. Only the owner and company admins can read or change its drafts. Remove the password, or make the Site private, to give editors their access back.
- The Site leaves its share holders' list of Sites. They open it like any visitor, by its address and the password.

## What a visitor sees

In place of the Site, a visitor sees **This site is password protected**, a **Password** field and **Open site**. The page names nothing about the Site, and search engines are asked not to index it.

- **Each page load asks again.** The password opens the Site for that page load only. A reload, a new tab or coming back asks again, and an open page asks again after 8 hours.
- **A wrong password** shows "That password isn't right. Try again." The same message shows when the Site can't be opened at all.
- **Too many tries** shows "Too many tries. Wait a few minutes, then try again."

Changing or removing the password ends every page that's open with the old one.

## Password rules

A Site password has at least 6 characters, at most 72 bytes, and at least one letter, one digit and one symbol. A symbol is any character that isn't a letter or a digit, a space included. Nothing is trimmed, and nothing else is required.

Only a public Site can be given a password. A branch never can: it's always private.

## Private Sites keep their password

Making a password Site private keeps its password. Making it public again asks visitors for that same password. Only removing the password takes it away.

The API never returns a password. It shows whether a Site has one with two fields on every Site:

| Field | Means |
| --- | --- |
| `password_protected` | `true` while the Site is public and asks for a password |
| `password_updated_at` | When the password was last set, while the Site keeps one, whatever its visibility. `null` when it has none |

Read `password_updated_at` to know whether a Site has a password, and `password_protected` to know whether visitors are asked for it now. A protected Site's `visibility` is `public`, so in a company's list of Sites, `filter[visibility]=public` returns protected Sites too.

## Set, change or remove the password

The Site's owner, or a company admin, sets the password.

<Note>
Site passwords need the Sites gateway, which isn't on for every company yet. Until it is, you can remove a password but not set one. To turn it on, [contact support](/help/getting-help).
</Note>

### With the CLI

In the Site's folder, with the owner's login (`--as member` for your own Site, `--as admin` for a company Site):

```bash
fluid sites password set
fluid sites password remove
```

`set` asks for the password twice at a prompt that doesn't echo it. The password is never an argument, and nothing the CLI prints holds it. Where there's no terminal, such as in CI, pipe it in:

```bash
printf %s "$SITE_PASSWORD" | fluid sites password set --password-stdin
```

`--public` makes a private Site public behind the password in one change, so it's never open without it. A refused password names the rule it broke, such as `password_too_short`.

`fluid sites visibility` and `fluid deploy --public` keep a Site's password, and say so: a protected Site shows as `public (password)`. Use `fluid sites password remove` to take the password away.

### In Mist

Open the Site's **Settings** and use the **Password** card: **Set password**, type it, then **Save password**. On a private Site, **Make public and protect** makes it public behind the password in one step. **Remove password** asks you to confirm first. Mist checks the rules before it sends the password, and never stores, logs or shows it.

Mist's agent never sees a password. It can open the **Password** card for you, and it refuses to pass a password through `fluid sites password` or an API call.

### From an AI client

The Fluid MCP server has `site_password_set` and `site_password_remove` for admins, and `my_site_password_set` and `my_site_password_remove` for your own Sites. `make_public` makes a private Site public behind the password in one step. A refusal comes back with its code and a fix. See [Build and deploy a Site from Claude](/sites/deploy-from-claude#the-tools).

<Warning>
A password you give an AI client passes through its model and stays in the chat. Type it yourself in Mist or with `fluid sites password set` when that matters.
</Warning>

### With the API

As the Site's owner, [change the site](/api-reference/sites/change-a-site) through the Member API:

```bash
curl -X PATCH "https://api.fluid.app/api/member/v2026-10/sites/{id}" \
  -H "Authorization: Bearer $MEMBER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "password": "fall-2026!" }'
```

- `{ "password": "..." }` sets or changes the password. `{ "password": null }` removes it.
- `{ "visibility": "public", "password": "..." }` makes a private Site public behind the password in one change.

As a company admin, [change the member site](/api-reference/member-sites/change-a-member-site) through the company API, with `application_themes.update`:

```bash
curl -X PATCH "https://api.fluid.app/api/company/v2026-10/member-sites/{id}" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "member_site": { "password": "fall-2026!" } }'
```

Use an admin's own login. A company API token never changes a member's Site, and changes a company Site only where Fluid has turned that on; see [Deploy from CI or an agent](/sites/quickstart#deploy-from-ci-or-an-agent).

## Errors

A refused password change answers `422` in the usual [error shape](/sites/member-api#errors). `error.details.error` names the code, and `error.details.password` holds the message:

```json
{
  "status": 422,
  "error": {
    "message": "Password must include a symbol",
    "details": {
      "error": "password_needs_symbol",
      "password": ["Password must include a symbol"]
    }
  },
  "meta": { "request_uuid": "…", "timestamp": "…" }
}
```

| Code | Means |
| --- | --- |
| `password_too_short` | Under 6 characters |
| `password_too_long` | Over 72 bytes. A character outside plain ASCII, such as `é` or an emoji, takes 2 to 4 bytes |
| `password_needs_letter` | No letter |
| `password_needs_digit` | No digit |
| `password_needs_symbol` | No symbol |
| `password_requires_public` | The change would leave the Site private. Send `"visibility": "public"` with the password |
| `password_not_for_branch` | The Site is a branch, which is always private |
| `password_unavailable` | The Sites gateway isn't on for the company yet |
| `suspended` | The Site is [taken down](/storefront/sites#when-a-site-is-taken-down), so removing the password would leave it public. Send `"visibility": "private"` with it, or have an admin bring the Site back first |
