The Fluid MCP server, at `https://mcp.fluid.app/mcp`, has tools that read, create, deploy and roll back company Sites. An AI client such as Claude Code builds the Site on your machine, then deploys the build through these tools, with no Fluid CLI.

<Warning>
  On the production MCP server, the read tools and the [member tools](#build-your-own-sites-as-a-member) work today. The `site_*` write tools need the [root-access pilot](#who-can-use-them), which isn't open in production yet. For [server functions](/sites/functions), deploy with the [Fluid CLI](/sites/quickstart): `fluid deploy`.
</Warning>

## Connect

Add the server to your client and sign in with your Fluid account when it asks. In Claude Code:

```bash
claude mcp add --transport http fluid https://mcp.fluid.app/mcp
```

The sign-in screen says what the client may do. To let it use the write tools, tick **Let this app make changes**. The box is off by default. If you signed in without it, your client doesn't list the write tools: remove the server, add it again and tick the box. For how agents connect to Fluid, see [Connect AI tools](/guides/connect-ai-tools).

## The tools

| Tool | What it does |
| --- | --- |
| `sites_list` | Lists a company's Sites. Takes `owner_kind`, `cursor` and `limit` |
| `site_get` | One Site and, for a company Site, its ten latest deployments with their bundle ids |
| `site_create` | Creates a company Site, private and empty. Takes `name` and `handle` |
| `site_deploy` | Publishes files sent inline in one call, or a built folder in two calls. With `branch`, it deploys to a preview branch instead. It doesn't publish server functions |
| `site_visibility_set` | Makes a Site `public` or `private` |
| `site_rollback` | Makes an earlier published deployment live again. Takes `site_id` and the deployment's `bundle_id` |
| `site_template_get` | A starter's files: `html`, the default, with no build, or `vite` |
| `site_branches_list`, `site_branch_promote`, `site_branch_delete` | List a Site's preview [branches](/sites/source-and-branches#branches), make a branch's published version live, or delete a branch |
| `site_logs`, `site_traffic` | A Site's log lines, such as uploads, publishes and rollbacks, and its visits, errors, top pages and referrers over `24h`, `7d` or `30d` |
| `site_env_list`, `site_env_set`, `site_env_unset` | A Site's environment variables. A value is a secret unless you send `secret: false`, and no answer shows a secret's value |
| `site_seo_get`, `site_seo_set` | A company Site's search title, description and image, and whether indexing is on. Indexing stays off until you send `indexable: true` |

Every tool takes the company's `company_id`. `companies_list` lists the companies you can reach.

### Who can use them

This list covers the `site_*` tools. The member tools have their own rules, in [Build your own Sites as a member](#build-your-own-sites-as-a-member).

- **Reads** need an admin of the company whose role grants `application_themes.view`, or a Fluid root admin in the pilot that gives root access through MCP, the root-access pilot.
- **Writes** need all of these:
  - you're a Fluid root admin in the root-access pilot;
  - the client is Claude Code or claude.ai;
  - you ticked **Let this app make changes** when you signed in, less than 7 days ago. After 7 days the client asks you to sign in again;
  - `application_themes.update` in the company. Root admins hold it.

Every tool needs Sites turned on for the company. Deploys, logs, traffic and env vars also need the [sites gateway](/sites/deployments). Without them, a call answers `sites_not_enabled`. If `sites_list` works but one of those calls answers `sites_not_enabled`, the gateway is what's off. A client that may not use the write tools doesn't see them in its tool list.

Each write is logged with who made it, the client and the Site.

## Create a Site

`site_create` makes a company Site that's private and has nothing published. Always pass a `handle`: lowercase letters, digits and single hyphens, at most 40 characters. If the call times out, it may still have made the Site. Calling again with the same handle answers that the handle is taken, where a call with no handle would make a second Site.

The `site_*` tools act on company Sites. A member makes their own Sites with the member tools.

## Build your own Sites as a member

A member, such as a rep, can list, create, deploy and share their own Sites from chat, signed in with their own Fluid login. These tools need no admin role and no root access:

| Tool | What it does |
| --- | --- |
| `my_sites_list` | Lists your own Sites in a company, newest first, with each one's `url`, `share_url`, visibility and status |
| `my_site_create` | Creates a Site you own, private and empty. Takes `name` and `handle` |
| `my_site_deploy` | Deploys the live version of one of your own Sites. Takes what `site_deploy` takes except `branch`, which it refuses |
| `my_site_visibility_set` | Makes one of your own Sites `public` or `private` |

To use them, tick **Let this app make changes** when you sign in, and be an active member of the company the call names. Sites must be on for that company. `my_site_deploy` also needs the sites gateway. A Site you don't own answers as not found.

## Deploy from a chat

A chat with no shell deploys in one call. Call `site_template_get` for a starter. `html`, the default, is a plain page with no build that loads the SDK from `/_fluid/sdk/v1/sites.js`. Edit its files, then call `site_deploy` with `site_id` and `files`, each path mapped to its `content` (UTF-8 text) or `content_base64` (such as an image). Fluid stores, checks and publishes them, and answers with the Site's live `url`. Send `config/meta.json` as `meta` and `config/access.json` as `access`, or as files at those paths.

- Inline files hold at most 512 KB in all, 256 KB each, and 100 files. A larger deploy is refused with `inline_too_large`. Deploy a built folder instead, or use `fluid deploy`.
- Fluid saves inline files to the Site's source repository, so `fluid sites pull` and Mist see them.

## Deploy a built folder

The client builds the Site first, such as with `npm run build`, then deploys the build folder in two calls.

**1. Send the manifest.** Call `site_deploy` with `site_id` and `files`: each file's path in the build, such as `/index.html`, mapped to its `sha256` (hex), `size` in bytes and `contentType`. You can also send `routes`, and the Site's `schema`, `access` and `meta`: the contents of `db/schema.json`, `config/access.json` and `config/meta.json`.

```json
{
  "company_id": "0192…",
  "site_id": "0193…",
  "files": {
    "/index.html": { "sha256": "9f2c…", "size": 812, "contentType": "text/html" },
    "/assets/index-4f1a.js": { "sha256": "b71e…", "size": 48211, "contentType": "text/javascript" }
  },
  "meta": { "default": { "title": "Spring launch" } }
}
```

The answer has a `bundle_id` and `uploads`.

**2. Upload the files.** `PUT` each file listed in `uploads` to its URL, with exactly the headers it lists. Files Fluid already stores aren't listed.

**3. Publish.** Call `site_deploy` again with the same `site_id` and the `bundle_id`, and no `files`. The answer has the Site's live `url`. Publishing replaces what's live.

Limits:

- At most 500 files a deploy, each up to 25 MiB. Deploy a larger build with `fluid deploy`.
- An upload URL expires after 60 minutes. After that, start again from the first call.
- A file the checks refuse comes back as `refused`, with a `code`, a `message` and the file's `path`. Fix it and start again.

### Schema changes that delete data

When the Site's `schema` drops or rewrites a table or column, the publish call comes back `refused` with the code `destructive_change_unconfirmed`. It lists each migration id and, in words, what it would lose. Nothing is published. Show that to the person, and only after they say yes, call again with `confirm_migrations` set to those ids. See [Change the schema](/sites/database#change-the-schema).

### What the client needs

To deploy a built folder, the client needs a shell, or another way to run the build, hash each file and send `PUT` requests to the upload URLs. Claude Code can. A chat client with no shell deploys the files it writes inline instead. See [Deploy from a chat](#deploy-from-a-chat).

A built-folder deploy through MCP doesn't save the Site's source in git. An inline deploy saves the files it sent. `fluid deploy` and `fluid sites publish` do. See [Source and branches](/sites/source-and-branches).

## Make it public

`site_visibility_set` with `public` lets anyone with the address open the Site. `private` leaves it to company admins and the members its shares admit. A new Site is private. See [Who can open a Site](/sites/overview#who-can-open-a-site).

## Roll back

Call `site_get` to list the latest deployments, then `site_rollback` with the `bundle_id` of the one to bring back. It's live at once, with no upload.

## Plain HTML

A Site doesn't need a framework. A published Site serves the Sites SDK at `/_fluid/sdk/v1/sites.js`, so a page with no build step can import it:

```html
<script type="module">
  import { fluid } from "/_fluid/sdk/v1/sites.js";
  const viewer = await fluid.auth.me();
</script>
```

See [Plain HTML](/sites/frameworks/html).

## Example in Claude Code

After connecting the server, ask in a project folder:

```text
Build a one-page Vite and React Site for our spring launch: a hero, three product
cards and a sign-up button. Create it as a company Site in Yoli with the handle
spring-launch, deploy the build, and give me the URL. Keep it private.
```

Claude Code scaffolds and builds the project, calls `site_create`, hashes the files in `dist/`, calls `site_deploy` with the manifest, uploads the listed files, and calls `site_deploy` again to publish. It answers with the Site's address. To make it public, ask it to, and it calls `site_visibility_set`.
