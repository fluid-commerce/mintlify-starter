A server function is a small piece of server code that belongs to your Site, such as a form handler, a webhook or a REST endpoint. Each one answers at `/api/<name>` on the Site's own host. Your page calls it with `fluid.fn`, a server calls it with a Site API key, and Fluid can run it on a schedule.

To build a Site whose functions serve a REST API, step by step, see [Serve a REST API from a Site](/sites/rest-api).

<Note>
  Functions need the sites gateway, which Fluid turns on for each company. Until then, a Site's API keys, environment variables and logs answer `404`, and schedules don't run. To turn it on, [contact support](/help/getting-help). Publish functions with Fluid CLI Sites plugin 0.1.349 or later, or Mist 1.19.0 or later, and call them from the page with `@fluid-app/sites` 0.1.71 or later.
</Note>

## Write a function

The quickest start is `fluid sites functions new`, from Sites plugin 0.1.360 or later. It writes a starter that fits the access and schedule you pick, adds the function to `config/functions.json`, and writes the context's types to `functions/fluid-env.d.ts`:

```bash
fluid sites functions new rsvp --access signed_in
fluid sites functions new partner-webhook --access key
fluid sites functions new nightly-digest --access key --schedule "0 6 * * *"
```

A function is a file at the top of the Site folder's `functions/` folder. Its file name is the function's name:

```text
my-event/
├── config/
│   └── functions.json      # who may call each function
├── functions/
│   ├── rsvp.ts             # answers /api/rsvp
│   ├── events.ts           # answers /api/events and /api/events/<anything>
│   └── lib/
│       └── validate.ts     # shared code: folders inside functions/ aren't functions
├── src/
└── package.json
```

- A function file ends in `.ts`, `.mts`, `.js` or `.mjs`. Its name is lowercase letters and digits in hyphen-separated runs, at most 40 characters, such as `nightly-digest`.
- Put shared code in a folder inside `functions/`. Every file at the top of `functions/` must be a function that `config/functions.json` names, except type declarations (`.d.ts`), such as `fluid-env.d.ts`.
- A Site has at most 20 functions.

Each function exports its handler as the default export. The handler takes the request and a context, and returns a `Response`:

```ts functions/rsvp.ts
import type { FunctionContext } from "./lib/types";

export default async function (request: Request, ctx: FunctionContext): Promise<Response> {
  if (request.method !== "POST") {
    return Response.json({ error: "method_not_allowed" }, { status: 405 });
  }
  if (ctx.caller.kind !== "page" || ctx.caller.viewer === null) {
    return Response.json({ error: "sign_in_required" }, { status: 401 });
  }

  // The Site's table rules don't apply to a function, so check the input here.
  const { eventId, guests } = await request.json();
  if (typeof eventId !== "string" || !Number.isInteger(guests) || guests < 1 || guests > 4) {
    return Response.json({ error: "invalid" }, { status: 422 });
  }
  const { data, error } = await ctx.fluid.db
    .from("rsvps")
    .insert({ event_id: eventId, guests, member_name: ctx.caller.viewer.name })
    .select();
  if (error) return Response.json({ error: error.code }, { status: 400 });

  return Response.json({ rsvp: data[0] }, { status: 201 });
}
```

The publish bundles each function with its imports, npm packages included, into one ES module. Functions run on Cloudflare Workers, not Node.js, so Node's built-in modules such as `node:fs` aren't available. Use web APIs such as `fetch`, `crypto.subtle`, `TextEncoder` and `URL`. A function that imports a Node built-in fails the build, and the publish stops before it sends anything.

### The request

`request` is a standard `Request` for the URL the caller used, with its method, query, headers and body. Fluid removes the caller's credentials before the function sees it: there is no `Authorization` or `Cookie` header. `X-Forwarded-For` is the caller's address.

### The context

| Field | What it holds |
| --- | --- |
| `ctx.site` | `{ id, handle, bundle, companyId }`: the Site and the published version that's running |
| `ctx.fn` | The function's name |
| `ctx.requestId` | The call's id. Log lines for the call carry it |
| `ctx.caller` | Who called. See below |
| `ctx.secrets` | Every [environment variable](/sites/env-vars) of the Site, secret or not, by name |
| `ctx.fluid.db` | The Site's own [database](/sites/database), as the Site |
| `ctx.fluid.api` | The Member API, as the signed-in visitor who made the call |

`ctx.caller.kind` says who called:

| `kind` | Who | Other fields |
| --- | --- | --- |
| `page` | The Site's page, through `fluid.fn`, with the visitor's sign-in | `viewer`: the signed-in visitor (`userId`, `name`, `avatarUrl`, `memberId`, `relation`), or `null` |
| `public` | A call with no sign-in and no key, a signed-out visitor's page included | None |
| `key` | A server with a Site API key | `keyId`, `keyName` |
| `schedule` | Fluid, on the function's `schedule` | `scheduledAt`: the UTC minute it runs for |

`fluid sites functions new` (Sites plugin 0.1.360 or later) writes the context's types to `functions/fluid-env.d.ts` as globals, `FluidFunction` and `FluidContext` among them, so a starter reads `export default (async (request, ctx) => …) satisfies FluidFunction`. The CLI replaces that file when the types change, so keep your own types elsewhere. With an older plugin, copy this type into `functions/lib/types.ts`:

```ts functions/lib/types.ts
export interface FunctionContext {
  site: { id: string; handle: string; bundle: string; companyId: string };
  fn: string;
  requestId: string;
  caller:
    | { kind: "page"; viewer: { userId: string; name: string; avatarUrl: string | null; memberId: string | null; relation: string } | null }
    | { kind: "public" }
    | { kind: "key"; keyId: string; keyName: string }
    | { kind: "schedule"; scheduledAt: string };
  secrets: Readonly<Record<string, string>>;
  fluid: {
    api: { fetch(path: string, init?: RequestInit): Promise<Response> };
    db: { from(table: string): any };
  };
}
```

### The answer

Return any `Response`. Fluid passes on its status, headers and body, with these changes:

- `Set-Cookie` is dropped, so a function can't set cookies. `Access-Control-*` headers are dropped too: the function's `cors` setting decides them.
- Without a `Cache-Control` of its own, the answer is sent with `Cache-Control: private, no-store`.
- A body over 10 MiB is cut off.

If the handler throws or returns something that isn't a `Response`, the caller gets `500` with `{"error": "fn_error", "requestId": "…"}`.

## Declare who may call it

`config/functions.json` names every function and says who may call it:

```json config/functions.json
{
  "version": 1,
  "functions": {
    "rsvp": { "access": "signed_in" },
    "events": { "access": "public", "cors": ["https://partners.example.com"] },
    "nightly-digest": { "access": "key", "schedule": "0 6 * * *", "timeoutMs": 20000 }
  }
}
```

| Setting | What it does |
| --- | --- |
| `access` | Required. `public`: anyone who may open the Site. `signed_in`: a signed-in visitor calling from the Site's page. `key`: a server sending one of the Site's API keys |
| `cors` | Exact origins, such as `https://partners.example.com`, that a browser page on another site may call the function from. None by default. The Site's own page never needs it |
| `schedule` | A five-field cron line in UTC that runs the function. See [Run a function on a schedule](#run-a-function-on-a-schedule) |
| `timeoutMs` | How long one call may run, from 1 to 30,000 milliseconds. Without it, a call may run 30,000 |

Access builds on the Site's own visibility. A `public` function on a private Site answers only the people the Site is shared with. A Site API key is the exception: it opens the Site's `key` and `public` functions whoever may open the Site, a private Site included. A key never opens a `signed_in` function.

The publish checks that the folder and the file match one for one, and refuses a function the file doesn't name, a name with no file, and two files for one name.

### Keep `/api/` free

A Site with functions can't hold a build file under `/api/`, where its functions answer. A Site with no functions serves its files there like anywhere else.

## Call a function

### From the Site's page

Use `fluid.fn.fetch` from `@fluid-app/sites`. It calls `/api/<name>` on the Site's own host and sends the visitor's sign-in, so `signed_in` functions see `ctx.caller.viewer`:

```ts
import { fluid } from "@fluid-app/sites";

const res = await fluid.fn.fetch("rsvp", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ eventId: "fall-gala", guests: 2 }),
});
if (res.ok) {
  const { rsvp } = await res.json();
}
```

The first argument is the function's name, then any sub-path and query: `fluid.fn.fetch("events/fall-gala?full=1")` calls `/api/events/fall-gala?full=1`. A path that would leave the function, such as one with `..`, throws a `TypeError`. `fluid.fn.fetch` returns the response whatever its status.

Call functions with `fluid.fn`, not with the page's own `fetch`. The page's session cookie never admits a function call, so a plain `fetch` reaches a `signed_in` function as a guest.

### From a server

A function answers at its Site's own host, `https://<label>.sites.fluid.app/api/<name>`, for every method. The rest of the path and the query reach the function, so one function can serve a whole resource:

```bash
curl https://primex-fall-gala.sites.fluid.app/api/events/fall-gala \
  -H "Authorization: Bearer $FALL_GALA_API_KEY"
```

Fluid gives the label when the Site is first published, and it never changes. It's normally your company's subdomain and the Site's handle, joined by a hyphen, such as `primex-fall-gala`. A longer or clashing one is shortened and ends in six characters of a hash. Don't guess it:

- After a publish, Sites plugin 0.1.360 or later prints each function's address, and `fluid sites publish --json` lists them as `functions`.
- The Site's `functions_url`, in the member and company APIs, is `https://<label>.sites.fluid.app/api/` once the Site is published. A server that doesn't send `functions_url` yet still has the label on the Site's page, where `window.location.origin` is the Site's own host.

## API keys

A Site API key lets a server call the Site's `key` functions. It starts with `fsk_` and is sent as `Authorization: Bearer <key>`. Each call checks the key, so a revoked key stops working at once.

- A key opens every `key` and `public` function of its Site. Keys have no narrower scopes. To limit what a partner reaches, give them a Site with only the functions they need.
- The function never sees the key. It sees `ctx.caller.keyId` and `ctx.caller.keyName`.
- A Site holds at most 20 live keys.
- The key's secret is shown once, when it's added. Fluid stores only a hash, and a list shows each key's first 12 characters.
- To rotate a key, add a new one, move your servers to it, then revoke the old one.

From the Site's folder, with Sites plugin 0.1.360 or later:

```bash
fluid sites keys create partner        # prints the secret once, alone on standard output
fluid sites keys list                  # names, first characters, last use; never a secret
fluid sites keys revoke partner        # by name, id or secret; asks first unless --yes
```

`keys create` prints only the secret to standard output and every message to standard error, so you can pipe the secret straight into a password manager or `fluid sites env set` of another Site. `--json` prints the whole key, secret included, as one line.

Or use the API, as the Site's owner:

- For a Site you own, with your own member token: [list](/api-reference/site-api-keys/list-a-sites-api-keys), [add](/api-reference/site-api-keys/add-an-api-key-to-a-site) and [revoke](/api-reference/site-api-keys/revoke-a-sites-api-key) a Site's API keys.
- For a company Site, as a signed-in admin with permission to change themes: [list](/api-reference/member-site-api-keys/list-a-company-sites-api-keys), [add](/api-reference/member-site-api-keys/add-an-api-key-to-a-company-site) and [revoke](/api-reference/member-site-api-keys/revoke-a-company-sites-api-key) a company Site's API keys. A company API token can't add one.

Keep a key on the server. Anything in the Site's build is public, so never put a key in the page.

## Run a function on a schedule

Give a function a `schedule`, a five-field cron line in UTC: minute, hour, day of month, month and day of week (`0` and `7` are both Sunday). Each field is `*`, a number or a range `a-b`, with an optional `/step`, in a comma list. Names such as `MON` aren't accepted.

```json
"nightly-digest": { "access": "key", "schedule": "0 6 * * *" },
"sync-inventory": { "access": "key", "schedule": "*/15 * * * *" }
```

- A schedule runs at most once every 5 minutes. A tighter one, such as `*/2 * * * *` or `0,3 * * * *`, is refused before the publish.
- Fluid sends the function `POST /api/<name>` with no body, and `ctx.caller` is `{ kind: "schedule", scheduledAt }`.
- Each minute runs at most once. A minute Fluid misses, during a deploy for example, is skipped, never run late, and a failed run isn't retried.
- Only the Site's current published version runs on its schedule.
- A scheduled function can still be called at `/api/<name>` like any other, under its `access`. Give it `"access": "key"`, and since any key opens every `key` function, return early unless `ctx.caller.kind` is `"schedule"` when only the schedule should run it.
- Only the status of a scheduled run is kept, in the [log](#logs-and-usage). Its answer is dropped.

## Environment variables and secrets

Set values with `fluid sites env set` and read them in a function from `ctx.secrets`:

```bash
fluid sites env set PARTNER_API_URL https://api.partners.example.com
printf %s "$STRIPE_SECRET_KEY" | fluid sites env set STRIPE_SECRET_KEY --secret --stdin
```

```ts
const stripeKey = ctx.secrets.STRIPE_SECRET_KEY;
```

Every value, secret or not, reaches every function of the Site in `ctx.secrets`, and none ever reaches the browser. A change reaches the deployed functions at once, with no new publish. There is no `process.env`. See [Environment variables and secrets](/sites/env-vars).

## Use Fluid data in a function

### The Site's database

`ctx.fluid.db.from(table)` queries the Site's database with the same builder as `fluid.db` in the page: `select`, `insert`, `update`, `delete`, the filters `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `in`, `is`, `like`, `ilike`, `not` and `match`, and `order`, `limit`, `range`, `single` and `maybeSingle`. Awaiting a query gives `{ data, error }`.

- A function queries **as the Site**, so your tables' row rules don't apply. Check who called with `ctx.caller` before you read or write on their behalf.
- `or()` isn't supported in a function yet, and `not()` takes `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `in`, `is`, `like` and `ilike`.
- A call made with a Site API key has its key checked again on each query, so a key revoked mid-call reaches no data.

### The Member API

`ctx.fluid.api.fetch(path, init)` calls the Member API as the signed-in visitor who called the function, with the same scopes as `fluid.api` in the page: `ctx.fluid.api.fetch("/orders")` is `GET /api/member/v2026-10/orders` for that visitor. Declare each scope it uses in `config/access.json`, as for the page. See [Use the Member API from a Site](/sites/member-api).

It needs a signed-in visitor. A call from a guest, a Site API key or a schedule answers `401` `fn_api_needs_viewer`, because a function has no credential of its own to call Fluid as the Site. For data a function needs without a visitor, keep it in the Site's database, or call another service with a secret from `ctx.secrets`.

### Other services

`fetch` reaches any HTTPS service. Keep its credentials in [secrets](/sites/env-vars).

## Limits

| Limit | Value |
| --- | --- |
| Functions per Site | 20 |
| Built module per function, with its imports | 10 MiB |
| Wall time per call | 30 seconds, or the function's `timeoutMs` |
| CPU time per call | 1 second |
| Outgoing requests per call (`fetch`, `ctx.fluid.db`, `ctx.fluid.api`) | 50 |
| Memory | 128 MiB |
| Request body and answer body | 10 MiB each |
| Calls per Site, every function and schedule together | 600 a minute |
| Shortest schedule | Every 5 minutes |
| Environment variables per Site | 64, each up to 5 KB |
| API keys per Site | 20 |

## What the answers mean

Fluid answers these itself, with a body of `{"error": "<code>"}`. Anything else is your function's own answer.

| Status and code | What it means | What to do |
| --- | --- | --- |
| `401` `sign_in_required` | A `signed_in` function was called with no signed-in visitor, or with a key, or the Site itself needs sign-in | Call it from the page with `fluid.fn` once the visitor signs in |
| `401` `fn_key_required` | A `key` function was called with no Site API key | Send `Authorization: Bearer fsk_…` |
| `401` `fn_key_invalid` | The key is unknown, revoked, or for another Site | Check the key, or add a new one |
| `403` `forbidden`, `404` `not_found` | The Site doesn't let this caller open it, such as a guest on a private Site | Share the Site, make it public, or use a key |
| `404` `fn_not_found` | The Site's published version has no function of that name | Check `config/functions.json` and publish |
| `405` `method_not_allowed` | A method other than `GET` or `HEAD`, on a Site whose published version has no functions, so `/api/` serves files | Publish the version with functions |
| `413` `body_too_large` | The request body is over 10 MiB | Send less |
| `429` `rate_limited` | The Site used its 600 calls this minute. `Retry-After` says when to try again | Wait, then retry |
| `500` `fn_error` | Your handler threw, or didn't return a `Response`. The body has the `requestId` | Fix the handler |
| `502` `fn_failed` | The function couldn't be run | Retry. If it persists, [contact support](/help/getting-help) with the time |
| `503` `fn_not_deployed`, `503` `unavailable` | The function isn't ready to run, or Fluid can't decide the call right now | Retry shortly |
| `504` `fn_timeout` | The call ran past its `timeoutMs` | Do less per call, or raise `timeoutMs` up to 30,000 |

## Publish functions

`fluid deploy` and `fluid sites publish` build and publish functions with the rest of the Site, and `fluid sites lint` checks them first with no request. Mist's **Publish** button runs the same command, from Mist 1.19.0. See [Publish a Site](/sites/publishing).

The Fluid MCP server's `site_deploy` tool publishes a built folder only, with no functions. Publish a Site that has functions with the Fluid CLI.

## Logs and usage

`fluid sites logs` shows one `function` line for each call: the function, who called (`page`, `public`, `key` or `schedule`), the request id, the status and how long it took, such as `rsvp answered 201 in 42 ms (page call, request 0199…)`. A timeout or a `5xx` is an `error` line, and a refusal such as the rate limit is a `warn` line. What your function prints with `console.log` isn't in the log, so return a useful status and body instead.

`fluid sites traffic` counts each function's calls, errors, timeouts and rate-limited calls, its wall time and the bytes it answered, by function and by caller. See [Logs and traffic](/sites/logs-and-traffic).

## Test a function

`fluid sites dev`, from Sites plugin 0.1.360 or later, runs functions on your machine: `/api/<name>` builds `functions/<name>.ts` on each call and runs it with Fluid's own function runtime, under the same access rules, CORS, header rules and timeout as the live Site. See [Develop a Site locally](/sites/local-development#functions).

```bash
fluid sites dev
curl http://127.0.0.1:9500/api/events/fall-gala
curl -H "Authorization: Bearer fsk_local" http://127.0.0.1:9500/api/partner-webhook
curl -X POST http://127.0.0.1:9500/_fluid/fn/_dev/fire/nightly-digest
```

Then publish the Site while it's private, and call the function from its page, or with `curl` and a Site API key. You can also call a handler directly in a unit test, with a `Request` and a stand-in context.
