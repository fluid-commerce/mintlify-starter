Fluid hosts two kinds of project. Most projects should be a **site**. Pick an **app** only when the project needs something a site can't do.

## The rule

Make it a site, unless it needs one of these:

| The project needs | Make it | Why |
| --- | --- | --- |
| Its own domain, such as `events.yoli.com` | App | Sites live at your company's addresses and have no custom domain |
| Server rendering, such as a Next.js app with server components or API routes that render pages | App | A site serves the files your build wrote |
| Heavy server code: long jobs, large dependencies, a Postgres database | App | Site functions are light handlers with a short time limit |

Everything else is a site: landing pages, event pages, calculators, forms, small dashboards, anything a static build with a little server code can do.

## Side by side

| | Site | Mist app |
| --- | --- | --- |
| Code | Any static build: Vite, Astro, plain HTML, Next.js static export | Next.js, from Fluid's starter |
| Deploy | `fluid deploy` | Push to the app's repository |
| Database | `fluid.db`, tables in `db/schema.json` | Its own Postgres |
| Server code | [Functions](/sites/functions) | Full Next.js server |
| Address | Your company's site address | Your own domain, or Fluid's |
| Read more | [Sites quickstart](/sites/quickstart) | [Mist apps](/mist-apps/overview) |

## Changing your mind

A site that outgrows these limits becomes an app in one step, with its data and settings. See [Convert a site to an app](/sites/convert-to-app).

Claude Code and other agents connected to Fluid follow the same rule when you ask them to build something.
