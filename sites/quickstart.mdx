Three commands take you from an empty folder to a public site.

## Before you start

- Node.js 24 or later.
- Git, which `fluid deploy` uses to save the site's source.
- A Fluid login for a company that has sites turned on. If publishing answers `404`, [contact support](/help/getting-help) to turn them on.

## Steps

<Steps>
  <Step title="Create the project">
    ```bash
    npm create @fluid-app/fluid-site my-event
    cd my-event
    ```

    This makes a Vite and React project with `@fluid-app/sites` already imported. `npx @fluid-app/create-fluid-site my-event` does the same. For a single HTML page and no build step, use the `html` template:

    ```bash
    npm create @fluid-app/fluid-site page -- --template html
    ```
  </Step>
  <Step title="Log in">
    ```bash
    fluid login
    ```

    If you don't have the Fluid CLI yet, install it first:

    ```bash
    npm install -g @fluid-app/fluid-cli @fluid-app/fluid-cli-member-site
    ```

    Then run `fluid --version`. On Node.js older than 24, npm quietly installs a much older release of the CLI, such as `0.1.6`, instead of the current one. Upgrade Node.js and install again.
  </Step>
  <Step title="Deploy">
    ```bash
    fluid deploy
    ```

    `fluid deploy` finds the framework, runs its build, creates the site the first time (a company Site with an admin login, your own Site with a member login), publishes the build and prints the site's link. Share that link: `https://yoli.com/home/sites/my-event` for a company Site, or your own credited `https://yoli.com/<username>/sites/my-event` for your Site. An older CLI prints the plain `https://yoli.com/sites/my-event` instead. It opens the same Site, but don't share it: share `https://yoli.com/home/sites/my-event`, or `https://yoli.com/<username>/sites/my-event` for your own Site, so the visit is credited correctly.

    The first deploy asks whether to make the site public. Pass `--public` to skip the question. Without a terminal to ask on, the site stays private until you run `fluid sites visibility public`.

    Before it publishes, `fluid deploy` commits the folder and pushes it to the site's source repository, so `fluid sites pull` can clone it later. Pass `--no-source` to publish without saving the source. See [Source and branches](/sites/source-and-branches).
  </Step>
</Steps>

Run `fluid deploy` again after each change. Files Fluid already holds aren't uploaded again.

## Already have a project?

Skip the first step. Run `fluid deploy` in the folder of any Vite, Astro, plain HTML or Next.js static export project. It builds the project with the package manager its lockfile names. See the [framework guides](/sites/frameworks/vite) for what each one needs.

A Next.js app that needs a server isn't deployed: `fluid deploy` explains why and creates nothing. See [Site or App?](/sites/site-or-app).

## Deploy from CI or an agent

Where you can't run `fluid login`, such as in CI, set `FLUID_TOKEN` and `FLUID_API_BASE`. The CLI reads `FLUID_TOKEN` before any saved login, and a token from `FLUID_TOKEN` has no default API base, so set `FLUID_API_BASE` to `https://api.fluid.app` too.

The token must be a signed-in person's:

- For a company Site, an admin's login whose role may change themes (`application_themes.update`). A company API token can list and read company Sites, but it can't publish them.
- For a member's own Site, that member's login.

Pass `--as admin` or `--as member` to say which it is, so a mismatch stops before any request.

An agent with no terminal to answer in can still sign in as a person, in two steps. The first emails that person a code, and the second redeems it and saves the login, so `fluid deploy` works without `FLUID_TOKEN`. `--yes` replaces a saved login for the same company without asking:

```bash
fluid login --send-code --email <email> --shop <shop>
FLUID_LOGIN_CODE=<code> fluid login --code --email <email> --yes --json
```

See [Connect AI tools](/guides/connect-ai-tools) for every way an agent signs in.
