Three commands take you from an empty folder to a public site.

## Before you start

- Node.js 24 or later.
- Git, which `fluid deploy` uses to save the site's source.
- A Fluid login for a company that has sites turned on. If publishing answers `404`, [contact support](/help/getting-help) to turn them on.

## Steps

<Steps>
  <Step title="Create the project">
    ```bash
    npm create @fluid-app/fluid-site my-event
    cd my-event
    ```

    This makes a Vite and React project with `@fluid-app/sites` already imported. `npx @fluid-app/create-fluid-site my-event` does the same. For a single HTML page and no build step, use the `html` template:

    ```bash
    npm create @fluid-app/fluid-site page -- --template html
    ```
  </Step>
  <Step title="Log in">
    ```bash
    fluid login
    ```

    If you don't have the Fluid CLI yet, install it first:

    ```bash
    npm install -g @fluid-app/fluid-cli @fluid-app/fluid-cli-member-site
    ```

    Then run `fluid --version`. On Node.js older than 24, npm quietly installs a much older release of the CLI, such as `0.1.6`, instead of the current one. Upgrade Node.js and install again.

    <CliUpToDate />
  </Step>
  <Step title="Deploy">
    ```bash
    fluid deploy
    ```

    `fluid deploy` finds the framework, runs its build, creates the site the first time (a company Site with an admin login, your own Site with a member login), publishes the build and prints the site's link. Share that link: `https://yoli.com/home/sites/my-event` for a company Site, or your own credited `https://yoli.com/<username>/sites/my-event` for your Site. An older CLI prints the plain `https://yoli.com/sites/my-event` instead. It opens the same Site, but don't share it: share `https://yoli.com/home/sites/my-event`, or `https://yoli.com/<username>/sites/my-event` for your own Site, so the visit is credited correctly.

    The first deploy asks whether to make the site public. Pass `--public` to skip the question. Without a terminal to ask on, the site stays private until you run `fluid sites visibility public`.

    Before it publishes, `fluid deploy` commits the folder and pushes it to the site's source repository, so `fluid sites pull` can clone it later. Pass `--no-source` to publish without saving the source. See [Source and branches](/sites/source-and-branches).
  </Step>
</Steps>

Run `fluid deploy` again after each change. Files Fluid already holds aren't uploaded again.

## Already have a project?

Skip the first step. Run `fluid deploy` in the folder of any Vite, Astro, plain HTML or Next.js static export project. It builds the project with the package manager its lockfile names. See the [framework guides](/sites/frameworks/vite) for what each one needs.

A Next.js app that needs a server isn't deployed: `fluid deploy` explains why and creates nothing. See [Site or App?](/sites/site-or-app).

## Deploy from CI or an agent

Where you can't run `fluid login`, such as in CI, set `FLUID_TOKEN` and `FLUID_API_BASE`. The CLI reads `FLUID_TOKEN` before any saved login, and a token from `FLUID_TOKEN` has no default API base, so set `FLUID_API_BASE` to `https://api.fluid.app` too.

The token must be one of these:

- For a company Site, an admin's login whose role may change themes (`application_themes.update`), or a company API token. A token creates, publishes and rolls back company Sites, including their database, functions, schedules and environment variables, and sets their visibility, password and **Required** setting, but it can't save the Site's source, so pass `--no-source`:

  ```bash
  FLUID_TOKEN=<company API token> FLUID_API_BASE=https://api.fluid.app \
    fluid deploy --as admin --public --no-source
  ```

  These need an admin's login, and a token gets 403 ("This needs a signed-in admin"): sharing the Site, featuring it or making it the members' home, deleting it, its API keys, the company vault, its SEO settings, and reading its database rows from the API. To do those, sign in as an admin as shown below. A token also reads only the call lines of the Site's log, never what its functions printed.

  Because a token can't delete a Site, an agent or CI job that publishes throwaway Sites, such as previews or tests, should publish to the same handle each run rather than a new one, and ask an admin to delete the ones it no longer needs.

  To publish to the same Site again, the folder needs the `.member-site.json` that names the Site. The first `fluid deploy` writes it, but a new checkout or CI runner doesn't have it: the source commit leaves it out, and `fluid sites pull` refuses a company API token with `403`. Bind the folder to the Site with `fluid sites link` (Sites plugin 0.1.521 or later), then deploy. It writes `.member-site.json` and downloads nothing:

  ```bash
  FLUID_TOKEN=<company API token> FLUID_API_BASE=https://api.fluid.app \
    fluid sites link fall-launch --as admin
  FLUID_TOKEN=<company API token> FLUID_API_BASE=https://api.fluid.app \
    fluid deploy --as admin --no-source
  ```

  `fluid sites link` takes the Site's handle or id. Without it, `fluid deploy` tries to create the Site again and stops with `Slug is already taken`, and names the `fluid sites link` command to run. If the Site runs server functions, the folder must hold them, with `config/functions.json`: `fluid deploy` refuses a folder without them rather than remove the live functions, unless you pass `--remove-functions`. With an older plugin, commit `.member-site.json` to your own repository after the first deploy instead. It holds the Site's id, handle and owner, the API address and file hashes, and no secret.

  A Site published with `--no-source` keeps its source repository as it was. So `fluid sites pull` gets the version before, and publishing from that pull puts the older version back. Publish a token's changes from the folder the token published from.

  What a company API token can and can't do with a company Site, at a glance:

  | A token can | A token can't |
  | - | - |
  | Create a Site, with `fluid deploy` or the API | Delete a Site |
  | Publish, with `--no-source`, and roll back | Save the source, or `fluid sites pull` it |
  | Bind a new folder with `fluid sites link` | Share a Site, feature it or make it the members' home |
  | Set visibility, a password and **Required** | Preview a page signed in with `fluid sites preview-url`, which needs a member's login. See [Check a signed-in page from a headless browser](/sites/passport#check-a-signed-in-page-from-a-headless-browser) |
  | Publish the database, functions and schedules, and set environment variables and secrets | Create a Site API key, use the company vault, change SEO settings, or read database rows from the API |
  | Read the call lines of the Site's log | Read what its functions printed or threw |
  | | Use the Fluid MCP server, which signs in with a person's Fluid account |
- For a member's own Site, that member's login.

Pass `--as admin` or `--as member` to say which it is, so a mismatch stops before any request.

An agent with no terminal to answer in can still sign in as a person, in two steps. The first emails that person a code, and the second redeems it and saves the login, so `fluid deploy` works without `FLUID_TOKEN`. `--yes` replaces a saved login for the same company without asking:

```bash
fluid login --send-code --email <email> --shop <shop>
FLUID_LOGIN_CODE=<code> fluid login --code --email <email> --yes --json
```

See [Connect AI tools](/guides/connect-ai-tools) for every way an agent signs in.
