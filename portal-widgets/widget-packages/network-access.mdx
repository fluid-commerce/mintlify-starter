Network access is an advanced capability for reviewed packages that need a public HTTP API. Prefer props, data sources, or typed portal functions when the host can supply the data.

## Decide whether network access is appropriate

Do not use worker network access for:

- secrets or credentials;
- OAuth flows;
- private endpoints;
- private API tokens;
- webhooks or background work.

Use a typed portal function or server application for those requirements.

## Declare the capability

Import [`networkAccess`](/portal-widgets/reference/widget-worker-sdk/variables/networkAccess) from the public worker facade and add it to the widget's `uses` array.

```ts
import {
  defineWidget,
  networkAccess,
} from "@fluid-app/portal-sdk/widgets/worker";

const weatherSummary = defineWidget({
  name: "WeatherSummary",
  component: WeatherSummary,
  uses: [networkAccess],
});
```

## Understand approval

A portal author must approve the exact package ID, package version, and capability version. Changing any of those values makes the prior grant stale.

Interactive portal push requests approval. For a reviewed non-interactive push, use `--allow-network-widgets`. The general `--yes` flag does not grant network access.

## Understand the request boundary

Granted fetch uses the worker's native origin. Fluid does not add credentials, cookies, tokens, or headers. Your `RequestInit`, including credential mode, remains in effect.

Approval doesn't bypass the browser's CORS checks or the host page's Content Security Policy. The destination must allow cross-origin requests from the portal's origin.

The Fluid-hosted portal's Content Security Policy lets pages and their workers connect only to:

- the portal's own origin;
- `https://api.fluid.app`;
- `https://auth.fluid.app`;
- Fluid's widget storage, `https://storage.googleapis.com/portal-widgets/`.

A widget worker loaded from Fluid's widget storage runs inside the portal page's policy. On the hosted portal, the browser therefore blocks a request to any other host, even when the package has network access approved. Check the request in the portal itself, not only in local development, before you rely on a third-party API. When the data has to come from another host, use a typed portal function or a server application instead.

A widget can send portal data it receives to an external service. Review both the package and its destinations before approval.

## Test failure states

Render a useful state for timeouts, unavailable destinations, malformed responses, rate limits, and offline use. Network failure must not crash the widget.
