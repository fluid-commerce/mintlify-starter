## Start with the right workspace

A Portal widget runs in a worker. It cannot read the Portal page's CSRF meta tag or use an authenticated tenant API client. There is no built-in Droplet query portal function. Network access grants do not provide this bridge, and the member-storefront `createQueryClient` helper is not a Portal worker API.

You need access to **both** the widget project and the Portal host project. The host must register and deploy a custom typed portal function. If Mist has only the widget workspace, stop and request the host integration; do not invent a function or fall back to cross-origin fetch.

<Warning>
The UUID examples require the UUID-aware Droplet query backend and the Portal adapter to be deployed together. A standalone extension-only Portal adapter does not accept this request. Merged source is not proof of deployment. Check the deployed contract before running the example; do not silently retry with another selector.
</Warning>

## Configure the Droplet once

Register the Droplet with its required `name` and `embed_url`, configure its canonical `data_url`, and install it in the member's company. Copy the public `uuid` returned by the management API, such as `drp_acme_rewards`; do not use a database UUID or guess an identifier. Read the authorized management response back and confirm `data_url` equals the intended receiver URL before proceeding: an older deployment may ignore an unknown field. `widget_data_url` remains a deprecated compatible alias, not another destination. See [registration and receiver setup](/themes/member-storefront/droplet-data#register-the-destination-and-save-the-secret).

The Droplet must remain available, operational, and actively installed. UUID queries do not require a theme extension or a member storefront site. The Portal still requires its own signed-in session and an active native member in the trusted company. Keep the Droplet secret on the receiver server; neither the worker nor the host browser receives it.

## Define one typed operation

Put this module in code shared by the worker build and the Portal host build. These are your application-owned names, not built-in SDK methods. Use the installed [worker reference](/portal-widgets/reference/widget-worker) to confirm `definePortalFunction` is available.

```ts title="member-echo-contract.ts"
import { definePortalFunction } from "@fluid-app/portal-sdk/widgets/worker";

export type MemberEcho = { member: { id: string; public_id: string; external_id: string | null } };
export const readDropletMember = definePortalFunction<MemberEcho>({
  capability: "acme.droplet-member",
  version: "1",
  method: "read",
});
```

This deliberately takes no worker-supplied member, company, Droplet, operation, or URL. The host fixes the Droplet and allowlisted `member.echo` operation; the server derives the authenticated member. Adapt the return type to your receiver's verified signed member shape rather than assuming arbitrary upstream fields are safe to display.

## Implement the function in the Portal host

The following code runs in the **Portal host**, never in the worker. The Portal homepage supplies `meta[name="csrf-token"]`. Read it for each request and use the same-origin dated Portal route with session cookies and CSRF. This is not the Bearer-authenticated Member API on another host. The Portal response wraps the receiver's object in `data`; errors use the Portal `error` envelope.

```js title="droplet-member-host.js"
import { implementPortalFunction } from "@fluid-app/portal-sdk";
import { readDropletMember } from "./member-echo-contract";

export function createDropletMemberBridge(dropletUuid) {
  let disposed = false;
  const pending = new Set();
  const implementation = implementPortalFunction(readDropletMember, async () => {
    if (disposed) throw new Error("Portal session scope ended");
    const csrf = document.querySelector('meta[name="csrf-token"]')?.content;
    if (!csrf) throw new Error("Portal CSRF token is unavailable");
    const controller = new AbortController();
    pending.add(controller);
    try {
      const response = await fetch("/api/member/v2026-10/droplet-queries", {
        method: "POST", credentials: "same-origin", cache: "no-store", redirect: "error",
        signal: controller.signal,
        headers: { Accept: "application/json", "Content-Type": "application/json", "X-CSRF-Token": csrf },
        body: JSON.stringify({ droplet_uuid: dropletUuid, operation: "member.echo", params: {} }),
      });
      const result = await response.json();
      if (disposed || controller.signal.aborted) throw new Error("Portal session scope ended");
      if (!response.ok) throw new Error("Droplet data is unavailable");
      const member = result.data?.member;
      if (!member || typeof member.id !== "string" || typeof member.public_id !== "string" ||
          !(member.external_id === null || typeof member.external_id === "string")) {
        throw new Error("Unexpected Droplet result");
      }
      return { member: result.data.member };
    } finally { pending.delete(controller); }
  });
  return {
    implementation,
    dispose() {
      disposed = true;
      for (const controller of pending) controller.abort();
      pending.clear();
    },
  };
}
```

Register `bridge.implementation` in the host's existing `FluidProvider` configuration as `remoteWidgets.functions: [bridge.implementation]`, preserving any other registered functions. If you configure `RemoteWidgetRegistryProvider` directly, use its `functions` prop. Do not invent a `portalFunctions` prop or override a built-in function. See [portal functions](/portal-widgets/widget-packages/portal-functions).

**Tie the bridge to the host's trusted authentication lifecycle.** Create one bridge for the current signed-in scope. On sign-out, account/company change, or host teardown, call `dispose()`, clear private UI, and unmount that scope's worker. Create a new bridge and remount the worker for the next scope. These are application integration responsibilities, not SDK session hooks. Abort alone does not detect a silently changed cookie, and this example does not claim background revocation monitoring. If the host cannot provide that lifecycle, do not ship private data with this bridge.

Do not retry a 401 or 403 with cached private data. Clear the current view and hand control to the host's existing sign-in/access flow. Keep upstream diagnostics server-side; do not display `error.details.backend_response` verbatim or expose secrets.

## Call it from the worker

Import the same `readDropletMember` value and include it in `defineWidget({ ..., uses: [readDropletMember] })`. Call `await readDropletMember()` from your component's load action. Render only the fields your application has approved, using normal text rendering. Handle rejection as an unavailable state, clear prior private results before another load, and cancel/ignore the component's pending continuation on unmount. The host's authentication transition must also unmount the worker, so its old private state cannot remain visible.

Do not call `fetch` on the Portal endpoint from the worker, inspect host DOM, place a Bearer token in properties, or invoke an invented `getDropletData` method. The worker receives only the typed result of its declared function.

## Implement a read-only receiver

At `data_url`, verify the exact raw bytes using the Droplet secret and `verifySignature` from `@fluid-app/droplet-sdk`, including timestamp freshness, before parsing JSON. Verify the signed company/shop binding and authorize the read. Follow the [raw-body verification example](/themes/member-storefront/droplet-data#verify-the-raw-body); do not reserialize JSON before verification.

For `member.echo`, require empty `params` and return `{ member: query.member }` from the **verified signed payload**, unchanged. Do not fabricate member fields, trust a member identifier from `params`, or fetch another member to construct the echo. Reject other operations and malformed identity objects. Keep this operation read-only and return only the member fields the signed payload already authorizes; do not log the payload or secret.

A Node receiver can implement the echo after checking the raw signature as follows. `request` is the incoming Web `Request`; supply `FLUID_DROPLET_SECRET` from the receiver's server-only secret storage. This example performs no backend write or member lookup.

```js title="member-echo-receiver.js"
import { verifySignature } from "@fluid-app/droplet-sdk";

export async function receiveMemberEcho(request, secret) {
  if (!secret) return new Response("Receiver is not configured", { status: 503 });
  const rawBody = Buffer.from(await request.arrayBuffer());
  const verified = verifySignature({
    rawBody, secret,
    timestamp: request.headers.get("x-fluid-timestamp"),
    signature: request.headers.get("x-fluid-signature"),
  });
  if (!verified.valid) return new Response("Invalid signature", { status: 401 });
  let query;
  try { query = JSON.parse(rawBody.toString("utf8")); }
  catch { return new Response("Invalid JSON", { status: 400 }); }
  const member = query?.member;
  if (!Number.isInteger(query?.company?.id) || query.company.id <= 0 ||
      !query.company.fluid_shop || query.company.fluid_shop !== request.headers.get("x-fluid-shop") ||
      !member || typeof member.id !== "string" || typeof member.public_id !== "string" ||
      !(member.external_id === null || typeof member.external_id === "string") ||
      query.operation !== "member.echo" || !query.params || Array.isArray(query.params) ||
      typeof query.params !== "object" || Object.keys(query.params).length !== 0) {
    return new Response("Unsupported query", { status: 422 });
  }
  return Response.json({ member: query.member }, { headers: { "Cache-Control": "private, no-store" } });
}
```

## Give Mist a complete task

> Build a Portal worker that calls the application-owned `readDropletMember` typed function and displays its approved member fields. Follow the Portal Droplet data guide. Verify host project access, deployed UUID support, active installation, and the host auth-scope disposal/remount integration before writing the widget. Do not use a worker fetch, the member-storefront helper, fake member data, or a built-in Droplet method. If the host bridge is missing, report that prerequisite.

Before calling the integration complete, test two real member scopes, missing installation, rejected CSRF, unknown operation, signature/timestamp failure, and sign-out/account switch while a response is delayed. The old bridge must reject late results and the old worker must be unmounted. Test the deployed contract, not merely source merge status or successful asset downloads.
