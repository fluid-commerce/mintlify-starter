A member site's templates carry the site's structure and menus. They don't carry the viewer's data. A site gets that data in its own JavaScript, through `window.fluid`. This page covers each method, who gets data back, how to handle a failure and how to declare what your scripts use.

## Know how a script reaches the viewer

A site renders in a [sandboxed frame](/member-sites/templates#know-the-frames-rules) with no cookie, so a bare `fetch` to a Fluid API carries no session and fails. The site SDK installs `window.fluid` in the frame instead. A call travels from the frame to Fluid's page around it, and from there to the member API as the viewer. Fluid forwards only routes it allows. Site management routes, such as a site's files and pages, aren't reachable from site code.

The SDK loads through `content_for_header`, so print it in your layout's `<head>`. Then a script calls `fluid` directly:

```js assets/site.js
const target = document.querySelector("[data-greeting]");

async function showGreeting() {
  if (!target || fluid.viewer() !== "member") return;
  try {
    const me = await fluid.me.get();
    target.textContent = `Welcome back, ${me.first_name}`;
  } catch (error) {
    // Keep the page usable. The empty element and its fallback stay as they are.
    console.warn("Could not read the member", error.code);
  }
}

showGreeting();
```

The page prints an empty element for the script to fill:

```liquid pages/index.liquid
<p data-greeting>Welcome to {{ site.name }}</p>
```

Render the structure in Liquid and fill the viewer's data in from the script. Show a neutral fallback while a call is pending and when it fails. Load the script with `script_tag`: see [Use tags and filters](/member-sites/templates#use-tags-and-filters).

<Warning>
  Never put a member's data into Liquid output or a `<script>` through a template variable. Never call a Fluid API with `fetch`, `XMLHttpRequest` or a form post from a site. The frame has no session, so those calls fail.
</Warning>

## Call the methods

Each method needs a scope. You declare the scopes in [`config/access.json`](#declare-the-scopes-you-use).

| Call | What it does | Scope |
| --- | --- | --- |
| `fluid.me.get()` | Reads the signed-in member. See [Show the signed-in member](/api-reference/me/show-the-signed-in-member) | `profile: read` |
| `fluid.me.update(fields)` | Changes the member's details and returns the member. Send at least one field. See [Update the signed-in member](/api-reference/me/update-the-signed-in-member) | `profile: write` |
| `fluid.tasks.list()` | Lists the member's tasks. See [List the member's tasks](/api-reference/tasks/list-the-members-tasks) | `tasks: read` |
| `fluid.tasks.complete(id)` | Completes a task. See [Complete a task](/api-reference/tasks/complete-a-task) | `tasks: write` |
| `fluid.tasks.reopen(id)` | Reopens a task. See [Reopen a task](/api-reference/tasks/reopen-a-task) | `tasks: write` |
| `fluid.team.list({ under })` | Reads the member's team tree. Pass `under` with a team member's id to read that member's branch | `widgets: read` |

`fluid.team.list` needs `widgets: read`, not a `team` scope, because the team tree comes from a member storefront native widget route.

`fluid.viewer()` returns `"member"` or `"guest"`, never throws and needs no scope. It reports whether a member is signed in. It doesn't say whether the calls return data: see the next section.

`fluid.fetch(path, init)` sends a request that Fluid allows, as `fetch` does. Lint can't see which scope a `fluid.fetch` call needs, so use the methods above when one fits.

## Know who gets data

Only the signed-in owner of a member-owned site gets data from these calls, and only while viewing the site published.

| Viewer | What the calls return |
| --- | --- |
| The member who owns the site, viewing it published | Data |
| Another signed-in member, including one the site is shared with | Nothing. The calls fail |
| A guest | Nothing. `fluid.viewer()` returns `"guest"` and every call fails with the `guest` error |
| Anyone viewing a company site | Nothing, because a company site has no member owner. A signed-in member there is a visitor |

- **Sharing grants nothing.** Sharing a site or making it public doesn't change who gets data. The calls return data for the owner only. See [Share a member site](/member-sites/sharing).
- **A company site can't use viewer data.** If you want a script to read the viewer, build a member-owned site. Build a company site from Liquid's structure and menus only.
- **A script that works for you may fail for a visitor.** Test with a second member, and show a fallback when a call fails.

## Handle a failure

A failed call throws a `FluidSdkError`. It has a `code`, the HTTP `status`, the `path` the call requested and the parsed `body` of the response when there was one. Branch on `code`.

| `code` | What happened |
| --- | --- |
| `guest` | No member is signed in |
| `refused` | Fluid refused to forward the request |
| `busy` | Fluid is busy, and the request wasn't sent. Try again |
| `too_large` | The request body is too large |
| `unsupported_body` | The request body isn't JSON |
| `http` | The member API answered with an error status. `status` and `body` carry it |
| `invalid_response` | The call succeeded but the response didn't hold the expected data |

A refusal from the member API, such as a viewer who isn't the owner, arrives as an `http` error with that status. Catch every failure and keep the page usable:

```js assets/site.js
try {
  await fluid.tasks.complete(taskId);
} catch (error) {
  if (error.code === "busy") {
    showMessage("Try again in a moment.");
  } else {
    showMessage("We couldn't complete that task.");
  }
}
```

## Declare the scopes you use

List the scope of each call your scripts make in `config/access.json`. The file is one JSON object with one key, `uses`:

```json config/access.json
{
  "uses": ["profile: read", "tasks: read", "tasks: write"]
}
```

`fluid member-site lint` warns on a script call whose scope the file lacks, so run it before you push. A site with no `config/access.json` isn't checked this way. The file is published with the site.

[Declare what a member site uses](/member-sites/access-declarations) lists every scope you can declare and explains how to write, publish and check the file.

## Keep scripts working with the published site

A script in `assets/` is live as soon as you push it, while page content stays a draft until you publish. Write a script that still works with the published pages. For example, a script that looks for `[data-greeting]` and does nothing when it isn't there works before and after the page that prints it is published.
