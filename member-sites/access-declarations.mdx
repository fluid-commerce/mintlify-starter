A member site's pages can read the signed-in viewer's profile and, through the site SDK, call the member API as that viewer. Because a site is code its owner wrote, Fluid doesn't give that code the viewer's data by default. A site asks for what it uses in one file, `config/access.json`, and Fluid grants only what the file lists.

This page lists everything a site can ask for and what each entry grants. It also covers who gets the grant, when it takes effect and how to check a declaration before you publish it.

<Note>
  Member sites must be turned on for your company by Fluid. To ask for them, [contact support](/help/getting-help). This page is about member sites, not about the pages a theme's [member storefront](/themes/member-storefront/member-sites) groups into sites.
</Note>

## Know how a declaration works

- **A site with no declaration behaves as it did before.** The owner of a member's site sees their full profile and can use the site SDK. Every other signed-in viewer sees `first_name` and `avatar_url` and gets no SDK data. Every viewer of a company site sees the same two fields and gets no SDK data.
- **A declaration takes effect when the site is published.** Fluid reads the declaration the site last published, never the draft. Editing the file changes nothing until you publish.
- **A declaration limits what the site can ask for. It never widens what a route allows.** The routes that no site can reach, and the routes a site can read but not change, stay that way for every declaration. A guest gets nothing either way.
- **A declaration limits the owner too.** The owner sees what a viewer would see, so what you preview is what a viewer gets.
- **A company site takes no declaration.** The file API refuses `config/access.json` on a company site, and a company site never lists it.

## Write a declaration

`config/access.json` is one JSON object with one key, `uses`. It holds a list of strings, and each string is a member field or a scope.

```json config/access.json
{
  "uses": [
    "member.first_name",
    "member.rank",
    "orders: read",
    "tasks: write"
  ]
}
```

This declaration lets the site print the viewer's first name and rank in Liquid, read the viewer's orders and complete or reopen the viewer's tasks. It asks for nothing else.

- A **member field** is `member.<field>`, such as `member.first_name`. It controls what the `member` object holds in Liquid.
- A **scope** is `<area>: read` or `<area>: write`, such as `orders: read`. It controls what the site's JavaScript can call.
- The file is at most 4 KiB and lists at most 64 entries, with no entry twice.
- Fluid refuses a file with an unknown key, an entry that isn't a string, an unknown field or area, a mode other than `read` or `write`, or `session: read`.
- `{ "uses": [] }` declares nothing. That is not the same as having no file. With no file, the site behaves as it did before. With an empty list, the site asks for nothing, so `member` holds no fields and the SDK reaches no data.

## Declare member fields

A site that has a declaration gets exactly the fields it lists, for every viewer the declaration reaches, the owner included. A declaration that lists only scopes gives `member` no fields. Once the file exists, a field it doesn't list prints nothing. That includes `first_name` and `avatar_url`, so list them if you print them.

| Field | What `member` holds |
| --- | --- |
| `member.first_name` | Given name |
| `member.last_name` | Family name |
| `member.full_name` | First and last names joined with a space |
| `member.email` | Email address for the membership in this company |
| `member.status` | Activity status in this company |
| `member.avatar_url` | Profile image URL, when available |
| `member.bio` | Profile biography, when available |
| `member.language_iso` | Saved language code, when available |
| `member.member_type` | The member type, so `member.member_type.slug` and `member.member_type.name` print |
| `member.rank` | The rank, so `member.rank.name` prints |

`member` stays set for a signed-in viewer whatever you declare, so `{% if member %}` still tells a signed-in viewer from a guest. A guest gets no `member`. See [Member variables](/themes/member-storefront/member-variables#member-profile) for what each field holds.

```liquid
{% if member %}
  <h1>Welcome back, {{ member.first_name | escape }}</h1>
  <p>Rank: {{ member.rank.name | escape }}</p>
  <p>{{ member.email }}</p>
{% endif %}
```

With the declaration above, the email line prints nothing, because `member.email` isn't listed.

## Declare scopes

A scope names an area of the member API and a mode. It controls the calls the site's JavaScript makes through `window.fluid`, including `fluid.fetch`.

- **The mode comes from the request.** A `GET` or `HEAD` request needs `read`. Any other method needs `write`.
- **`write` doesn't include `read`.** A site that reads and changes an area declares both.
- **The area comes from the route.** Fluid decides which area a request belongs to from the route it reaches, so a request can't borrow another area's scope by changing its path.
- **A route with no area is refused.** A site that has a declaration can't call a member API route that appears in no area below.

| Area | What it covers |
| --- | --- |
| `addresses` | The member's saved addresses. Read only: a write is refused for every declaration |
| `agreements` | The agreements that apply to the member and their acceptance |
| `ai` | Conversations with the assistant, their messages and feedback |
| `calendar` | Calendar events and catch-ups |
| `carts` | The member's carts |
| `contacts` | Contacts and their notes and tasks, contact imports, groups and notes |
| `media` | Media, direct uploads, playlists and their items |
| `messages` | Conversations and messages |
| `mysite` | MySite settings, themes, links and statistics |
| `notifications` | Notification preferences, push devices and the activity feed. Push devices are read only |
| `orders` | The member's orders |
| `plan` | The member's Pro plan, the plans on offer and paid add-ons |
| `points` | The points balance and ledger |
| `profile` | The signed-in member and their profile and social links |
| `search` | Catalog search |
| `shares` | Tracked shares, referral shares and photo shares |
| `stats` | Dashboard totals and top assets |
| `subscriptions` | The member's subscriptions, their bundles, discounts and waivers. Read only: a write is refused for every declaration |
| `tasks` | The member's tasks |
| `widgets` | The member storefront's native widget routes, such as schedules, sales goals and earnings goals |

A declaration never opens a route that the member API keeps off the browser. Saved payment methods, the member's companies, Exigo member data, and site management and shares stay refused for every site. The Site SDK page lists them.

`session: read` is never declared. Every call through the SDK needs the viewer's session first, so Fluid grants it to any declaration that holds at least one other scope. A declaration of member fields alone gets no SDK session, so the site's JavaScript reaches no data.

### Match the SDK calls

Each named SDK call needs one scope:

| Call | Scope |
| --- | --- |
| `fluid.me.get()` | `profile: read` |
| `fluid.me.update(fields)` | `profile: write` |
| `fluid.tasks.list()` | `tasks: read` |
| `fluid.tasks.complete(id)` and `fluid.tasks.reopen(id)` | `tasks: write` |
| `fluid.team.list({ under })` | `widgets: read` |
| `fluid.fetch(path, init)` | The scope of the route the path reaches, such as `orders: read` for `/api/member/v2026-10/orders` |

`fluid.team.list` needs `widgets: read`, not a `team` scope, because the team tree is served by a native widget route.

## Know who gets what

A declaration grants the most to the owner and to members the owner shared the site with. Everyone else sees the public minimum.

| Viewer | No declaration | A declaration |
| --- | --- | --- |
| Guest | No `member`, no SDK data | No `member`, no SDK data |
| Owner | All ten fields and every scope | The declared fields and scopes |
| Member the site is shared with | `first_name` and `avatar_url`, no scope | The declared fields and scopes, limited by what the site declared when it was shared |
| Any other signed-in member of a public site | `first_name` and `avatar_url`, no scope | `first_name` and `avatar_url`, no scope |
| Company admin with no share | `first_name` and `avatar_url`, no scope | `first_name` and `avatar_url`, no scope |
| Any viewer of a company site | `first_name` and `avatar_url`, no scope | Not applicable, because a company site takes no declaration |

- **A viewer outside the audience gets nothing extra.** Declared fields and scopes go to the owner and to members a share matches, and never to a visitor of a public site or to an admin because of their role. A public site that declares `orders: read` can't read the orders of everyone who opens it.
- **An admin is another viewer.** An admin who opens a member's private site gets the declared grant only through a share that matches them, as any member does.
- **A site whose owner is no longer an active member grants no scope to anyone.** Every viewer sees `first_name` and `avatar_url`.
- **Viewers aren't asked to approve a declaration.** A share holder never sees a prompt for the scopes a site declares. The owner chooses who to share with, and an admin can take a site down.

### Share a site that declares scopes

A share records the declaration the site had published when the owner created it. The share holder gets the site's current declaration, limited to what the recorded one also held.

- **A later publish never widens a share.** If you publish a declaration that adds `tasks: write` after sharing, the people you already shared with don't get it. To grant the new scope, share the site with them again.
- **A later publish can narrow a share.** If you publish a declaration that drops a scope, every share holder loses it on their next call.
- **A share made before the site declared anything grants no scope.** The holder gets `first_name` and `avatar_url`. Share the site again after you publish a declaration.
- **Narrowing is immediate.** A take-down, a deleted share, an owner who is no longer active and a publish that drops a scope all refuse the viewer's next call. Fluid checks the site on every request.

## Publish, change and remove a declaration

Write the file with the file API, or with the CLI by editing the pulled folder and pushing it. A declaration you write is a draft until the site publishes.

- **Publish.** Publishing the site makes the declaration live together with the settings.
- **Change.** Edit the file and publish again. The next call from every viewer follows the new declaration.
- **Remove.** Delete `config/access.json` and publish. The site returns to the behavior it had with no declaration.
- **Copy.** A member's copy of a member's site starts with the original's published declaration as its own draft. A company admin's copy of a member's site starts with none. After that, changes to either site never change the other.
- **Company sites.** The file API refuses the path on a company site, and `fluid member-site push` leaves it alone.

The Build a site with the API page and the `fluid member-site` reference explain how to write files, push and publish.

## Check a declaration

Run `fluid member-site lint` in a pulled folder before you push. It sends no request.

- **An invalid file is an error.** Lint reports each problem the file API would refuse: an unknown key, field, area or mode, an entry that isn't a string or appears twice, `session: read`, more than 64 entries and a file over 4 KiB.
- **An undeclared use is a warning.** When the file is valid, lint warns for each `member.<field>` a Liquid file reads and each SDK call a script makes that the declaration lacks. A warning doesn't fail the command. A site with no `config/access.json` isn't checked this way, because a site with no declaration isn't limited.

A site's published declaration is readable by the people it affects. The site's payload in the member API and the company API carries it as `access`, with `declared` and the list of `uses`. `declared` is `false` for a site that has published no declaration, and for a company site. A company admin sees it on the site's detail page in Fluid Admin.

## Handle a refusal

When a signed-in viewer's call needs a scope the site hasn't declared, the call fails with `403`. The error's `details` name the missing scope, so you can add it:

```json
{
  "details": {
    "error": "member_site_scope_undeclared",
    "scope": "orders: write"
  }
}
```

Only a viewer the site admits gets a refusal that names a scope. Every other refusal carries the same `details`, with `error` set to `member_site_unavailable`, so a response never says whether a site exists, is unpublished or was never shared. These refusals use that body:

- The site is missing, unpublished or taken down.
- The viewer isn't in the site's audience, or the site's owner is no longer an active member.
- The site has no declaration and the viewer isn't its owner, or the site is a company site.
- The route belongs to no area.

A guest's call fails with the SDK's `guest` error. The Site SDK page shows how each call reports a refusal.

## Fix a declaration

| You see | Why | What to do |
| --- | --- | --- |
| `{{ member.email }}` prints nothing | The site has a declaration that doesn't list `member.email` | Add `member.email` and publish |
| `403` naming `orders: read` | The site's JavaScript read orders and the declaration lacks the scope | Add `orders: read` and publish |
| A write to an area fails and a read works | `write` doesn't include `read`, or the route is read only | Declare the mode you need. `addresses` and `subscriptions` are read only |
| A share holder lacks a scope you added | The share recorded an older declaration | Share the site with them again |
| The CLI skips `config/access.json` | The site is a company site | Company sites take no declaration |
| The site ignores your edit | The declaration is still a draft | Publish the site |
