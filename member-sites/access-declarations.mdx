A member site's JavaScript can read the signed-in viewer's data and act as that viewer through the site SDK. Because a site is code its owner wrote, Fluid doesn't hand that code everything. A site says what it uses in one file, `config/access.json`, and Fluid lets the owner's code reach only what the file lists.

This page lists everything a site can declare and what each entry grants. It also covers who gets the grant, when it takes effect and how to check a declaration before you publish it.

<Note>
  Member sites must be turned on for your company by Fluid. To ask for them, [contact support](/help/getting-help). This page is about member sites, not about the pages a theme's [member storefront](/themes/member-storefront/member-sites) groups into sites.
</Note>

## Know how a declaration works

- **A site with no declaration behaves as it did before.** The owner of a member's site can use the site SDK on every route the SDK allows. Every other signed-in viewer sees `first_name` and `avatar_url` and gets no SDK data. Every viewer of a company site sees the same two fields and gets no SDK data.
- **A declaration takes effect when the site is published.** Fluid reads the declaration the site last published, never the draft. Editing the file changes nothing until you publish.
- **A declaration limits the owner.** Only the site's owner can use the SDK, and a declaration narrows what the owner's code can reach to the scopes it lists. A call you forgot to declare fails for you first.
- **A declaration only narrows.** The routes that no site can reach, and the routes a site can read but not change, stay that way for every declaration. A guest gets nothing either way.
- **Nobody else gains anything.** Sharing a site, sharing it again and a site's declaration never give a share holder, an admin or a visitor a scope. They keep `first_name` and `avatar_url`.
- **A company site takes no declaration.** The file API refuses `config/access.json` on a company site, and a company site never lists it.

## Write a declaration

`config/access.json` is one JSON object with one key, `uses`. It holds a list of strings, and each string is a member field or a scope.

```json config/access.json
{
  "uses": [
    "profile: read",
    "orders: read"
  ]
}
```

This declaration lets the owner's code read the signed-in member and their orders. It asks for nothing else, so a call to change the member's details is refused.

```js
const me = await fluid.me.get();
const response = await fluid.fetch("/api/member/v2026-10/orders");
```

`fluid.me.get()` needs `profile: read`, and `fluid.fetch` of the orders route needs `orders: read`. `fluid.me.update({ language: "es" })` would need `profile: write`, which this file doesn't list, so the call fails with a refusal that names it.

- A **scope** is `<family>: read` or `<family>: write`, such as `orders: read`. It controls what the site's JavaScript can call.
- A **member field** is `member.<field>`, such as `member.first_name`. See [Declare member fields](#declare-member-fields).
- The file is at most 4 KiB and lists at most 64 entries, with no entry twice.
- Fluid refuses a file with an unknown key, a repeated key, an entry that isn't a string, an unknown field or family, a mode other than `read` or `write`, or `session: read`.
- `{ "uses": [] }` declares nothing. That is not the same as having no file. With no file, the site behaves as it did before. With an empty list, the site asks for nothing, so the SDK reaches no data.

## Declare scopes

A scope names a family of the member API and a mode. It controls the calls the site's JavaScript makes through `window.fluid`, including `fluid.fetch`.

- **The mode comes from the request.** A `GET` or `HEAD` request needs `read`. Any other method needs `write`.
- **`write` doesn't include `read`.** A site that reads and changes a family declares both.
- **The family comes from the route.** Fluid decides which family a request belongs to from the route it reaches, so a request can't borrow another family's scope by changing its path.
- **A route with no family is refused.** A site that has a declaration can't call a route that appears in no family below.

| Family | What it covers |
| --- | --- |
| `addresses` | The member's saved addresses. Read only: a write is refused for every declaration |
| `agreements` | The agreements that apply to the member and their acceptance |
| `ai` | Conversations with the assistant, their messages and feedback |
| `calendar` | Calendar events and catch-ups |
| `carts` | The member's carts |
| `contacts` | Contacts and their notes and tasks, contact imports, groups and notes |
| `media` | Media, direct uploads, playlists and their items |
| `messages` | Conversations and messages, and sending a message from a native widget |
| `mysite` | MySite settings, themes, links and statistics |
| `notifications` | Notification preferences, push devices and the activity feed. Push devices are read only |
| `orders` | The member's orders |
| `plan` | The member's Pro plan, the plans on offer and paid add-ons |
| `points` | The points balance and ledger |
| `profile` | The signed-in member and their profile and social links |
| `search` | Catalog search |
| `shares` | Tracked shares, referral shares and photo shares, including from a native widget |
| `stats` | Dashboard totals and top assets |
| `subscriptions` | The member's subscriptions, their bundles, discounts and waivers, and a native widget's subscription summary. Read only: a write is refused for every declaration |
| `tasks` | The member's tasks, including completing and reopening one from a native widget |
| `widgets` | The member storefront's native widget routes for data, schedules, sales goals and earnings goals. Reads and writes are separate scopes |

A declaration never opens a route that the member API keeps off the browser. Saved payment methods, the member's companies, Exigo member data, and site management and shares stay refused for every site. The Site SDK page lists them.

`session: read` is never declared. Every call through the SDK needs the viewer's session first, so Fluid grants it to any declaration that holds at least one other scope. A declaration of member fields alone gets no SDK session, so the site's JavaScript reaches no data.

### Match the SDK calls

Each named SDK call needs one scope:

| Call | Scope |
| --- | --- |
| `fluid.me.get()` | `profile: read` |
| `fluid.me.update(fields)` | `profile: write` |
| `fluid.tasks.list()` | `tasks: read` |
| `fluid.tasks.complete(id)` and `fluid.tasks.reopen(id)` | `tasks: write` |
| `fluid.team.list({ under })` | `widgets: read` |
| `fluid.fetch(path, init)` | The scope of the route the path reaches, such as `orders: read` for `/api/member/v2026-10/orders` |

`fluid.team.list` needs `widgets: read`, not a `team` scope, because the team tree is served by a native widget route.

## Declare member fields

A member field entry is `member.<field>`. The file accepts these ten fields, so a declaration that lists them stays valid:

| Field | What it names |
| --- | --- |
| `member.first_name` | Given name |
| `member.last_name` | Family name |
| `member.full_name` | First and last names joined with a space |
| `member.email` | Email address for the membership in this company |
| `member.status` | Activity status in this company |
| `member.avatar_url` | Profile image URL, when available |
| `member.bio` | Profile biography, when available |
| `member.language_iso` | Saved language code, when available |
| `member.member_type` | The member type |
| `member.rank` | The rank |

- **A field entry grants no SDK call.** Declaring `member.email` doesn't let the site's JavaScript call anything. To read the member in your script, declare `profile: read` and call `fluid.me.get()`.
- **Read viewer data in your script, not in Liquid.** Member data is leaving member site Liquid. A declaration doesn't change what a template prints, and `fluid member-site lint` warns for every Liquid file that reads `member.<field>`, whatever the declaration holds. A template should keep to the site's structure, such as its pages and menus.

## Know who gets what

Only the owner can use the SDK. The declaration decides how much.

| Viewer | No declaration | A declaration |
| --- | --- | --- |
| Guest | No SDK data | No SDK data |
| Owner of a member's site | Every scope | The declared scopes |
| Any other signed-in member, including a member the site is shared with and a visitor to a public site | `first_name` and `avatar_url`, no scope | `first_name` and `avatar_url`, no scope |
| Company admin who doesn't own the site | `first_name` and `avatar_url`, no scope | `first_name` and `avatar_url`, no scope |
| Any viewer of a company site | `first_name` and `avatar_url`, no scope | Not applicable, because a company site takes no declaration |

- **Sharing grants nothing.** Sharing a site, sharing it again and publishing a declaration never give a share holder a scope. A public site that declares `orders: read` can't read the orders of everyone who opens it.
- **An admin is another viewer.** A company admin who opens a member's site gets no scope because of their role. An admin can take the site down.
- **A site whose owner is no longer an active member grants no scope to anyone.** Its calls are refused, and a viewer the site still admits sees `first_name` and `avatar_url`.
- **Viewers aren't asked to approve a declaration.** Nobody but the owner uses a declared scope, so there's nothing for a viewer to approve.
- **Narrowing is immediate.** A take-down, an owner who is no longer active and a publish that drops a scope all refuse the next call. Fluid checks the site on every request.

## Publish, change and remove a declaration

Write the file with the file API, or with the CLI by editing the pulled folder and pushing it. A declaration you write is a draft until the site publishes.

- **Publish.** Publishing the site makes the declaration live together with the settings.
- **Change.** Edit the file and publish again. The next call follows the new declaration.
- **Remove.** Delete `config/access.json` and publish. The site returns to the behavior it had with no declaration.
- **Copy.** A member's copy of a member's site starts with the original's published declaration as its own draft. A company admin's copy of a member's site starts with none. After that, changes to either site never change the other.
- **Company sites.** The file API refuses the path on a company site, and `fluid member-site push` leaves it alone.

The Build a site with the API page and the `fluid member-site` reference explain how to write files, push and publish.

## Check a declaration

The CLI carries the file with the other site files:

- **`pull` writes it.** `pull` writes `config/access.json` into the folder when the site has a draft declaration. When the site no longer has one, `pull` deletes your local copy if you haven't edited it since the last pull or push. A copy you edited stays, unless you pull with `--force`.
- **`push` sends it.** `push` sends the file with the other site files, and a push with no edit sends nothing for it. `push` refuses an invalid declaration before it sends any request, so a bad file never leaves the settings and files half written.

Run `fluid member-site lint` in the folder before you push. It sends no request.

- **An invalid file is an error.** Lint reports each problem the file API would refuse: not valid JSON, a key other than `uses` or a repeated key, an entry that isn't a string or appears twice, an unknown field, family or mode, `session: read`, more than 64 entries and a file over 4 KiB.
- **A Liquid file that reads `member.<field>` is a warning.** Lint warns whatever the declaration holds, because member data is leaving member site Liquid. Read it in a script with `fluid.me.get()`, which needs `profile: read` in `config/access.json`.
- **An SDK call the declaration lacks is a warning.** When the file is valid, lint warns for each named SDK call a script makes whose scope the declaration doesn't list, such as `fluid.me.update(` without `profile: write`. A site with no `config/access.json` isn't checked this way, because a site with no declaration isn't limited.

A warning doesn't fail the command.

## See what a site declares

A site's published declaration is readable by the people it affects:

- The site's payload in the member API and the company API carries it as `access`, with `declared` and the list of `uses`. `declared` is `false` for a site that has published no declaration, and for a company site.
- The account menu shows one line of it under a company site or a site shared with the member, such as "Uses first name, orders (read)".
- A company admin sees the declaration on the site's detail page in Fluid Admin, next to the control that takes the site down.

The summary describes a declaration. It grants nothing.

## Handle a refusal

When the owner's call needs a scope the site hasn't declared, the call fails with `403`, and the error's details name the missing scope so you can add it.

Only the owner gets a refusal that names a scope. Every other refusal carries the same unavailable error, so a response never says whether a site exists, is unpublished or was shared. These refusals use it:

- The site is missing, unpublished or taken down.
- The viewer isn't the owner, whatever the site's visibility or shares.
- The site is a company site, or its owner is no longer an active member.
- The route belongs to no family, for a site that has a declaration.

A guest's call fails with the SDK's `guest` error. The Site SDK page shows how each call reports a refusal.

## Fix a declaration

| You see | Why | What to do |
| --- | --- | --- |
| `403` naming `orders: read` | The owner's code read orders and the declaration lacks the scope | Add `orders: read` and publish |
| A write to a family fails and a read works | `write` doesn't include `read`, or the route is read only | Declare the mode you need. `addresses` and `subscriptions` are read only |
| Lint warns about `member.<field>` in a Liquid file | Viewer data is leaving member site Liquid | Read it in your script with `fluid.me.get()` and declare `profile: read` |
| A share holder or admin gets no data | Only the owner uses a declaration | This is by design. Sharing grants nothing |
| The CLI skips `config/access.json` | The site is a company site | Company sites take no declaration |
| The site ignores your edit | The declaration is still a draft | Publish the site |
