A member site declares what it needs in small JSON files next to its build. They're published with the build, checked by `fluid sites lint` and `fluid sites publish`, and never served as files. Each one is optional.

```text
diamond-leaders/
  dist/                 the build output
  db/schema.json        the site's database, see Database
  config/access.json    the Fluid data the site uses
  config/meta.json      each page's title and preview
  config/routes.json    which file answers each path
```

The site's database is declared in `db/schema.json`. See [The member site database](/member-sites-v1/database).

## Fluid data the site uses

`config/access.json` lists the Fluid API scopes and member fields the site uses:

```json config/access.json
{
  "uses": ["member.first_name", "member.rank", "search: read", "orders: read"]
}
```

Each entry in `uses` is one of these:

- **A scope**, `<family>: read` or `<family>: write`. A `read` scope covers `GET` calls to the family's Member API routes, and a `write` scope every other method.
- **A member field**, `member.<field>`, that `fluid.auth.me()` returns in `viewer.fields`.

An entry is listed once, and `uses` holds at most 64 entries.

### What each visitor gets

A declaration is what the site asks for. What each visitor's calls may use is narrower:

| Visitor | Scopes for their calls | Member fields in `viewer.fields` |
| --- | --- | --- |
| The owner of a member's site | Every scope the site declares | Every field the site declares |
| A member of your company the site admits, and anyone on a company site | The declared scopes your company allows rep sites to use | `first_name` and `avatar_url`, plus the declared fields your company allows |
| A guest | None | None |

A site with no `config/access.json` gets no scope for anyone, its owner included. Its calls through `fluid.api` answer `403` with `scope_not_granted`.

Every call acts as the visitor, on the visitor's own data. A site never holds a company token and never reads another person's data through `fluid.api`.

### What your company allows

Your company decides which scopes rep sites may use on a visitor's data. By default that's the `read` scope of each family that holds no personal data, which today is `search: read`. Families that reach a visitor's personal or sensitive data, such as orders, subscriptions, addresses, contacts and points, and every `write` scope, are off until your company turns them on. No visitor sees a consent prompt: the company decides.

Admins read and change the list with [Read the company's member site policy](/api-reference/member-site-policy/read-the-companys-member-site-policy) and [Replace the company's member site policy](/api-reference/member-site-policy/replace-the-companys-member-site-policy).

The [Member API reference](/api/member-apis) lists each family's operations.

### Member fields

`first_name`, `last_name`, `full_name`, `email`, `status`, `avatar_url`, `bio`, `language_iso`, `member_type` and `rank`.

## Page titles and previews

The storefront writes each page's `<title>` and link preview tags (`og:title`, `og:description`, `og:image` and `twitter:card`) from `config/meta.json`. Link previews read these tags and never run your site's code.

```json config/meta.json
{
  "default": {
    "title": "Diamond Leaders",
    "description": "Events, training and products from the Diamond Leaders team.",
    "image": "/images/preview.png"
  },
  "pages": {
    "/events": {
      "title": "Events",
      "description": "Upcoming team calls and launches."
    },
    "/shop": {
      "title": "Shop",
      "description": "Products the team recommends.",
      "image": "https://cdn.yoli.com/images/fall-launch.jpg"
    }
  }
}
```

| Key | What it holds |
| --- | --- |
| `default` | The title and preview of every page not in `pages`. Required |
| `pages` | Titles and previews by exact path |
| `title` | Required, 1 to 200 characters |
| `description` | Optional, at most 500 characters |
| `image` | Optional: a file of your build, such as `/images/preview.png`, or an `https://` address |

As a visitor moves through a single-page app, the storefront also takes the page's `document.title` into its own tab title.

Each value is picked on its own: the page's entry in `pages`, then `default`, then the site's SEO settings, its own title, description and image, and last your store's defaults. A page with no `image` still gets the site's preview image. The storefront also writes the meta description, `og:url` and the canonical link: `/home/sites/<handle>` on your store domain, followed by the page's path. Search engines may index the page only while the site is a live, public company site, and `config/meta.json` can't change that. See [SEO and the page head](/storefront/sites#seo-and-the-page-head).

## Routes

`config/routes.json` says which file of your build answers a path. With no `config/routes.json`, every path that isn't a file is answered by `/index.html`, the fallback a single-page app needs:

```json
[{ "prefix": "/", "file": "/index.html" }]
```

For each request, the site's host looks for an answer in this order:

1. A file of the build at that path, such as `/assets/index-Bx3zQw9a.js`.
2. The path plus `/index.html`, so `/about` serves `/about/index.html`.
3. The first route whose `path` is the path, then the longest route whose `prefix` matches. A path whose last segment has a file extension, such as `/logo.png`, never falls back to a route: it's a missing file.
4. `/404.html` from your build, with status `404`, when the build has one.
5. Fluid's own not-found page.

A route is `{ "path": ..., "file": ... }` for one path, or `{ "prefix": ..., "file": ... }` for every path under a prefix:

```json config/routes.json
[
  { "path": "/events", "file": "/events.html" },
  { "prefix": "/blog/", "file": "/blog/index.html" },
  { "prefix": "/", "file": "/index.html" }
]
```

Every route must name a file of your build. A build with no `config/routes.json` must have an `index.html`. Your build can't hold a file under `/_fluid/`, because the site's host answers that path itself.
