You publish a member site with the Fluid CLI. `fluid sites publish` uploads your build output and declarations, and makes them the site's current version in one step. Until that step succeeds, the site keeps serving its current version.

For a direct API integration, see [Member Sites APIs](/api/member-sites) for the V1 publishing and sharing references.

## Before you start

Install the Fluid CLI and its member site plugin, and sign in:

```bash
npm install -g @fluid-app/fluid-cli @fluid-app/fluid-cli-member-site
fluid login
```

Your login follows the site's owner. A member's site is published with that member's login, and a company site with the login of an admin who may change themes. Say which one you're using with `--as member` or `--as admin`. Without it, the server decides and a refusal names the login the site needs.

`fluid sites publish` needs the folder's binding file, `.member-site.json`, which names the site. To start a new site, run `fluid sites create` in your site's folder. It creates the site and writes the binding there, and leaves your files alone:

```bash
fluid sites create diamond-leaders --name "Diamond Leaders" --as member
```

For a company site, add `--company` and use `--as admin`. A folder already bound to the same site is left as it is, and a folder bound to another site is refused.

## Check the site

`fluid sites lint` checks the site's folder on your machine. It makes no request and needs no login.

```bash
npm run build
fluid sites lint
```

It runs the same checks `fluid sites publish` runs before it sends anything:

- Every file of the build has a type a site may serve, such as HTML, CSS, JavaScript, JSON, SVG, images, fonts, text, XML, PDF, MP4, WebM and MP3.
- No file is under `/_fluid/`, and nothing in the build is a symbolic link.
- The build holds at most 2,000 files, each at most 25 MiB, and 250 MiB in all.
- The build has an `index.html` when there's no `config/routes.json`, and every route names a file of the build.
- `db/schema.json`, `config/access.json`, `config/meta.json` and `config/routes.json` are valid JSON and pass their rules.
- There's no `functions/` folder or `config/functions.json`. Server functions aren't available yet.

Each problem is an error that names its file. A clean folder prints nothing and exits `0`. Any error exits `1`.

The build's folder is `dist` by default. Name another with `--dir`, relative to the site's folder:

```bash
fluid sites lint ./diamond-leaders --dir build
```

## Publish

```bash
fluid sites publish
fluid sites publish ./diamond-leaders --dir build --as member
```

The command:

1. Hashes every file of the build. A file under `assets/` whose name carries a content hash, such as `index-Bx3zQw9a.js`, is cached by browsers for a year.
2. Reads `db/schema.json` and the files in `config/`.
3. Runs the checks of `fluid sites lint`, and stops before any request when one fails.
4. Uploads only the files the site doesn't store yet. Publishing the same build twice uploads nothing the second time, and changing one file uploads one file.
5. Publishes: applies the schema, creating the site's database on the first publish that has a `db/schema.json`, and makes the new build the site's current version.

A new site is private until its owner makes it public. Publish it, open it at its storefront address, and check it before you share it.

To go back to an earlier build, see [Make an earlier bundle current](/api-reference/site-bundles/make-an-earlier-bundle-current-roll-back). A build with a `db/schema.json` can't be made current again yet: restoring a site's database isn't available, so the rollback is refused with `no_database` and nothing changes. The other operations behind publishing are [Start a bundle upload](/api-reference/site-bundles/start-a-bundle-upload) and [Publish a bundle](/api-reference/site-bundles/publish-a-bundle), or for a company site [Publish a company site's bundle](/api-reference/member-site-bundles/publish-a-company-sites-bundle).

### Make a site public or private

`fluid sites visibility` sets who may open the folder's site:

```bash
fluid sites visibility public
fluid sites visibility private ./diamond-leaders --as member
```

`public` lets anyone open the site, and `private` only the people it's shared with. Use the owner's login: `--as member` for your own site, `--as admin` for a company site. Whatever its visibility, a draft or a site a company admin took down opens for nobody, and a site a company admin locked opens only for company admins. The command says so. See [Share a site](/member-sites-v1/overview#share-a-site).

### Confirm a destructive schema change

A change to `db/schema.json` that drops, renames or retypes a table or column, or makes a column required, needs a migration. Confirm each migration by its id, once per migration:

```bash
fluid sites publish --confirm 2026-11-20-rsvp-party-size
```

Without it, the publish is refused with `destructive_change_unconfirmed`, the command lists each unconfirmed migration with its steps, and nothing changes. See [Change the schema](/member-sites-v1/database#change-the-schema).

### Finish an interrupted schema change

If a publish leaves a schema change pending, the next publish offers to finish that bundle first. With no terminal, use:

```bash
fluid sites publish --finish-pending
```

That run finishes the pending bundle and stops. Run the command again for your own build. If the pending bundle needs destructive migration confirmations, check its schema and pass `--confirm-pending <id>` for each of its migrations. Your build's `--confirm` values are never applied to the pending bundle. See [Finish an interrupted publish](/member-sites-v1/database#finish-an-interrupted-publish).

## What the answers mean

| Answer | What it means | What to do |
| --- | --- | --- |
| `404` on the start | The site wasn't found for this login, or member sites aren't on for your company. Both answer the same `404` | Check the folder's `.member-site.json` and your login. If they're right, ask Fluid to turn member sites on |
| `409` `uploads_in_progress` | The site has 5 uploads in progress | Run it again once one finishes or expires, 60 minutes after it started |
| `409` on the publish | The bundle can no longer be published. Nothing changed | Run the command again for a new bundle |
| `422` | A check failed. The command names it and where, or the files that weren't stored. Nothing was published | Fix it and publish again |
| `422` `no_database` | The database is unavailable, or a branch is still waiting for its database copy. Nothing was published | On a branch, wait for the copy. If it stays unavailable, [contact support](/help/getting-help) |
| `409` `schema_change_pending` | An earlier publish's schema change timed out and may have run. Nothing from this build was published | Publish the version the answer names (`details.pendingBundle`) again. That finishes the change. On a terminal, the command offers to do it. Elsewhere, run it again with `--finish-pending`. Then publish your build again |
| `422` `destructive_change_unconfirmed` | The schema has a destructive change you didn't confirm | Run it again with `--confirm` for each migration listed |
| `502` | Fluid couldn't finish a step, and the bundle failed | Run it again |
| `504` `publish_timeout` | The publish ran out of time. The current version keeps serving | Nothing: the command sends it again, up to three times. After that, run the same command again. It's safe, and uploads no file again |
| `504` with no code | A proxy timed out, so the outcome is unknown and the build may still go live | Wait a minute, check what the site shows, then run it again without rebuilding |

The command never prints the upload addresses it uses.
